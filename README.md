# 读码机

给一个项目文件夹路径，独立判断代码行为是否符合**这个项目自己声明的规则**，不是套用通用linter规则；判断层的可靠性是量测出来的，不是假设的；确认的问题可以自动诊断、交给Claude Code或DeepSeek Harness（dsh）执行，执行完自动复检、用git diff区分"真实改动"和"判断噪音"。

## 作用、特点与优势

**作用**：给一个代码项目做体检，找出"行为不符合项目自己设计意图"的函数，自动诊断、给出最小化修复建议——确认要处理的话，直接交给Claude Code或DeepSeek Harness执行修复，执行完自动重新体检，确认这次改动是不是真的把问题解决了。

**特点**：

- **判断依据是这个项目自己现读现算出来的，不是套用一份通用规则库**——同一个函数放进不同项目，判断依据完全不同，因为它会先独立理解"这个项目自己声称该怎么运行"，再拿具体行为去对照，不是拿一份放之四海而皆准的规则手册去套。
- **判断和执行严格分离**——读码机自己从不写文件、不改代码，只产出判断和诊断建议，执行永远外包给已经有agentic能力的Claude Code/dsh，最终"要不要真的改"的确认权，始终留给使用者自己原生的确认机制，不是读码机自己实现一套能代替人按确认的东西。

**优势**（比"让AI自己审查自己代码"或者通用linter强在哪，下面有具体数字支撑，不是自我评价）：

- **主动测量自己的可靠性，不是闷头输出结论就完事**——判断层的噪音率、批分析的覆盖率、诊断层的复现率，全部是真实consensus/A-B测试量出来的数字，不是"我们认为很准"这种说法。
- **遇到自己的判断死角，有能力自己发现、自己修复**——开发过程中两次真实撞见自己的结构性缺陷，从发现、诊断、修复到重新验证，全部留有真实记录，不是设计时就想全了。
- **判断→诊断→执行→复检是完整闭环，不是给个建议就结束**——确认的问题能自动跑完诊断、交给执行者真实修复、修复完自动复检确认结果真的变好了，全链路验证过，不是停在"生成一份报告"这一步。

## 先看几个数字

这些都是真实测出来的，不是估算：

- **判断层噪音率：26%**——同一个函数、同样的材料，独立判断5次，结论不完全一致的概率（consensus测出）。
- **批分析覆盖率提升：57% → 19%**（"无法判断"比例）——同一个真实模块，单次整体分析 vs 分批分析的真实A/B对比。
- **大规模场景下的覆盖率天花板**：在一个109文件的真实第三方开源项目（deepseek-harness/packages/core）上测试，不同批次覆盖率从4.3%到47%不等，量化确认了"narrative探索预算有限，项目越大能覆盖的比例越低"这个现象。
- **诊断层复现率：5/5**——同一个已知问题跑5次独立诊断，全部给出一致结论、且比判断层本身更稳定。
- **真实闭环修复：3次以上**——诊断→交给执行者（Claude Code / dsh）→真实执行→自动复检确认结果变化，全链路验证，见下面的完整案例。
- **自我发现的结构性缺陷：2个**——复杂度门槛测不到"缺失调用"类bug、改前改后对比混入判断噪音——都是真实测试中撞见、诊断、修复、再验证过的，不是设计时就想到的。

## 这是什么问题

vibe coding场景下，AI生成代码的速度远超人工逐行审查的速度——不是"用户能力不够"，是这种工作方式下代码产出规模结构性地超过了人工审查能跟上的极限。市面上大部分工具要么是通用linter（不理解这个项目自己的设计意图），要么是"让AI自己审查自己的代码"（自己判自己的卷，天然有偏差）。

读码机的做法：先独立读一遍项目的代码和文档，现场推导出"这个项目自己声称该遵守的规则"（不是套用预设规则库），再拿具体函数的行为去对照——同时老老实实测量这套判断机制本身有多可靠，而不是假设它可靠。

## 一次完整的真实闭环（不是演示，是真实运行记录）

目标：`orders.py`里的`cancel_order`函数取消订单时没有释放预留库存，导致库存被永久占用。

**1. 读码机独立判断（真实consensus，一致率100%）**：

> `src/orders.py :: cancel_order`（一致率100%，✓ 诊断已核实）
>
> `cancel_order`（`src/orders.py` 第20-28行）只把订单状态改为`cancelled`并发送通知，没有调用`inventory.release_stock`。函数注释明确承认这是真实bug：预留库存被永久占用。全库搜索`cancel_order`没有任何调用方防护，问题在正常调用路径下必然触发。
>
> 最小化修复：在`cancel_order`中，把订单状态改为`cancelled`之前调用`inventory.release_stock(order.sku, order.quantity)`释放预留库存。

**2. 交给dsh（DeepSeek Harness）处理，dsh自己核实、修复、验证**：

> 核实诊断：`orders.py`的`cancel_order`确实无条件跳过库存释放，仓库自身的基线提交也印证这是真实缺陷。
>
> 运行时复现：用真实调用得到库存泄漏，bug坐实。
>
> 修改内容：在状态变更之前补上`inventory.release_stock(order.sku, order.quantity)`调用，完全保留原有设计意图。
>
> 验证结果（5个场景全部通过，含"重复取消会不会重复释放"这类边界情况）。

**3. 读码机自动复检，用git diff区分真实变化和判断噪音**：

```
=== 这次改动前后对比 ===
判断结果变化的函数（1个）：
  src\orders.py::cancel_order: undermine → support  ✓ 变好了（文件真的被改过，verifier已复核通过）
复杂度没有变化。
```

从诊断到执行到复检，全程没有一步用合成材料垫底，是真实的判断→执行→复检记录，不是拼出来的演示。

## 架构

```
两个入口                      判断引擎                人工确认      执行者
─────────                   ─────────                ────────     ────────
dialogue.py    ─┐                                                 ┌─ Claude Code（终端交接）
                 ├─→ 叙述锚定判断 → consensus → 诊断 ─→ 确认关口 ─┤
MCP工具×4       ─┘                                                 └─ dsh（web + 文档化交流）
                                                                          │
                                                                          ▼
                                                              复检 + git diff噪音过滤
```

对照Ledger + Observer + Brain + Executor(+Analysis)这套架构范式：读码机是**Observer + Analysis(+Ledger)**——只负责观察和分析，从不写文件、不改代码；**Brain故意做得很窄**，只决定"诊断哪些发现"，不决定"要不要应用修复"；**Executor这一环刻意留空**，外包给Claude Code或dsh这类已经有agentic能力的执行者。判断权始终留给人。

### 判断链路（七个环节）

1. **复杂度分析**——radon（Python）/ lizard（其它语言），确定性工具，零噪音，决定"值不值得深入描述"。
2. **行为契约描述**——LLM读代码给出行为描述，独立verifier核实结论有没有代码原文支撑。
3. **项目叙述生成**——agentic读代码，推导出这个项目自己声称该遵守的不变量，每条不变量必须标注具体证据范围（哪个文件、哪个入口），不允许从一个场景归纳出的规则被不加说明地套用到全部同类场景。
4. **行为判断**——拿函数的实际行为对照项目叙述，判断支持还是违反。
5. **consensus噪音测量**——同一个判断独立跑5次，测出真实复现率，不假设判断可靠。
6. **迭代信号分级**——按一致率把发现分层（确认/待核实/噪音），只有高一致率的才会往下走。
7. **诊断+修复建议**——针对确认的问题，agentic地重新查调用链，给出最小化修复建议。

<details>
<summary><b>一个真实撞见并修复的结构性缺陷</b>（点击展开）</summary>

复杂度门槛（只对B级以上函数生成行为描述）测不到"少调用了一次该调的函数"这类bug——这类问题不会拉高圈复杂度。真实测试中撞见后，加了"叙述点名救回"机制：项目叙述生成本身会在文本里点名具体函数，即使这些函数复杂度不够，只要被叙述点名，也会补一次行为描述、纳入判断范围。修复后真实验证：中型样本里被复杂度门槛跳过的`cancel_order`函数被正确救回、正确判定违反不变量——上面那次完整闭环案例里判对的那个函数，最初就是靠这个机制才进入判断范围的。

</details>

## 项目结构

```
读码机/
├── src/
│   ├── sensor/          读代码的底层能力（agentic读代码循环、MCP封装）
│   ├── observer/        判断链路（复杂度→行为→叙述→判断→consensus→迭代信号）
│   ├── analysis/        诊断层
│   ├── brain/           决策层（窄范围：只决定诊断什么）
│   ├── ledger/          分析产物的存取
│   ├── dialogue.py       读码机自己的对话框入口
│   └── judge_mcp_server.py   MCP协议暴露（供外部agent直接调用）
├── eval_set/             真实测试项目的完整分析报告样本
└── docs/04-当前功能参考.md   当前功能的完整参考
```

## 运行方式

```bash
pip install -r requirements.txt
cp .env.example .env   # 填入DEEPSEEK_API_KEY

python src/dialogue.py                    # 默认交给Claude Code处理
python src/dialogue.py --executor=dsh     # 交给dsh处理（web半自动衔接）
```

也可以作为MCP server暴露给已经在运行的Claude Code/dsh会话直接调用：

```bash
python src/judge_mcp_server.py
```

<details>
<summary><b>已知局限</b>（如实写，不回避，点击展开）</summary>

- **规模天花板**：narrative探索有步数预算限制，项目/批次越大，覆盖率越低（已量化：4.3%-47%）。目前建议场景限定在小型项目（约25个文件以内，走单次分析路径）；中大型项目的架构（批分析+跨批关联整合）已经建好并验证过机制本身可行，但覆盖率优化留到有真实需求时再做。
- **Claude Code执行路径**：交接机制本身验证过（任务描述正确传递、终端权限正常交接），但由于本地账号登录问题，还没有走完一次完整的"诊断→Claude Code真实执行→复检"闭环——目前完整闭环全部是通过dsh验证的。
- **批分析场景的改前改后对比**：单项目场景已经有git diff噪音过滤，批分析场景还是"改动前后各打印一遍"的粗糙版本，没有专门的diff函数。
- **没有独立前端**：目前是终端交互，dsh的web界面某种程度上可以当作前端使用，但还没有专门设计。
- **没有增量分析/缓存**：每次都是全量重新分析，没有"只重新分析改动过的部分"这个优化，是主要的成本来源之一。
- **diff-pr整合还没做**：设想中该项目会和[diff-pr](https://github.com/Pythondinner/diff-PR-claude-version-)（独立的、监控AI改动是否符合用户需求的合规性检查工具）组成互补的一对——一个查"改得对不对"（读码机），一个查"改得符不符合要求"（diff-pr）。整合方案已经设计清楚（复用diff-pr的判断核心，用读码机自己的确认发现列表+git diff代替diff-pr原本依赖的Claude Code Hook采集），还没动手实现。

</details>
