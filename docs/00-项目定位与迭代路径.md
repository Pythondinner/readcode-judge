## 0. 跟长期愿景的关系

这篇文档记的是"已经跑通、有真实数据支撑"的部分——0→3四步+两个修复+核实层，都是真的写了代码、真的测过的。**更大的长期愿景**（读码机只是"传感器"，后面还有裁判、记忆、决策器、执行器，最终变成"软件演化的自动驾驶仪"）记在 [02-迭代第一性原理-设计草案.md](02-迭代第一性原理-设计草案.md) 和 [03-自迭代读码机-设计讨论记录.md](03-自迭代读码机-设计讨论记录.md) 里——**这两篇是愿景和理论依据，不是已经验证过的东西，两者不要混为一谈**。

02文档里"行为/复杂度"类比自动剧本生成机的want/obstacle，类比本身是合理的洞察，但严格说不是同一种结构——want/obstacle是对抗张力（戏剧靠冲突推进），行为/复杂度更接近一个要最大化的目标函数（02文档自己第五节也是这么定位的，叫"梯度框架"），两者是启发关系，不是同构关系，02文档标题里"同构对照"这个说法稍微说满了。

03文档里"人工打分→训练裁判"那段类比RLHF不准确——RLHF是用人类偏好数据做梯度下降训练奖励模型，03文档实际设计的机制（存历史打分，检索相似案例当few-shot参考）没有任何模型训练/梯度更新，准确说是"检索增强的小样本校准"，机制本身没问题，叫法需要改。

03文档"围栏设计"部分质量较高、且已经被验证过一部分——L1证据围栏对应`verifier.py`，L3动作围栏对应`goal_loop.py`的生成→检查→诊断→修复，这两个不是空想，是今晚真实跑通过的机制。03文档指出的"prompt注入防御"这道防线，`agent.py`当时还没有，**现在已经补上**（见第7节）。

## 1. 这是什么，解决什么问题

一句话：**给一个代码库配一个能读它、答问题的 Agent，同时给这个 Agent 配一份能验证它答得准不准的考卷。**

要解决的真实问题：接手一个不熟悉的代码库很费时间，用 AI 帮忙读代码理论上能省时间，但直接把代码丢给 AI 问，有两个真实毛病——

1. 代码库大到一定程度，没法整个塞进上下文；
2. 没法知道 AI 说的对不对——它可能说得很像那么回事，其实理解错了，尤其是拿它来读一个自己不熟悉的代码库时，没有办法交叉验证。

读码机专门解决这两个毛病：第一个靠 context engineering（怎么翻文件、怎么管理读过的内容）解决；第二个靠一份可验证的考卷（evals）解决。同时因为它是"读代码"这件事，天然可以做成一个 goal loop——读→答题→跟标准答案核对→答错的地方针对性再去读→重答。

## 2. 三个不要混为一谈的东西

立项讨论里反复出现的一个纠偏：这个项目牵扯到三个技术方向（context engineering / evals / MCP），但**它们不是同一件事，也不是同时都要用力气**：

- **MCP**：只是"怎么接工具"这一层，跟代码库读没读懂没有直接关系，通不通用不影响agent聪不聪明。
- **Context engineering**：解决"代码库太大塞不进去"这个纯工程问题，改的是"怎么管理读过的内容"，不改变agent本身的理解力。
- **Evals**：解决"我怎么知道它读懂了没有"这个信任问题，是整个项目里**唯一能告诉你要不要往下走、往哪个方向改**的东西——考卷不是这个项目的一部分，考卷是这个项目的方向盘。

## 3. 目标代码库

第一期用 `自动剧本生成机` 自己练手——好处是出题人（项目作者本人）对这个代码库了如指掌，能自己判断agent答得对不对，不需要先花时间去弄懂一个陌生代码库才能验证考卷靠不靠谱。跑顺了之后再换一个陌生的开源仓库去测，那时候考卷才是唯一的真相来源，是真正的考验。

## 4. 起步考卷

第一版 12 题，四个难度层级都覆盖，题目和标准答案见 [eval_set/起步考卷.json](../eval_set/起步考卷.json)：

| 层级 | 测的是什么 | 判分方式 |
|---|---|---|
| 1. 单文件事实题 | 有没有真的翻对文件 | 精确匹配 |
| 2. 跨文件追踪题 | 能不能顺着代码追数据/调用关系 | 语义判断（关键点有没有提到） |
| 3. "为什么"类设计意图题 | 真理解还是背台词 | 语义判断，复用 `checker_include.py` 的"关键论点有没有出现"思路 |
| 4. 边界/否定题 | 会不会瞎自信地说"有这个功能" | 精确匹配（是/否） |

**这份考卷不是设计出来求全的，是先出一小批就去跑，跑完根据agent真实答错的地方再扩充**——不追求现在就覆盖所有可能的问题类型（[00-可复用设计原则与洞察.md](../../自动剧本生成机/docs/00-可复用设计原则与洞察.md)第2条"先跑再迭代，不要一开始就穷举"，同一条原则搬过来用）。

## 5. 迭代路径：四步走，不要一上来搭完整系统

**第 0 步（当前所在位置）：不写 Agent 代码，先验证考卷本身靠不靠谱。**
用一个现成的、有文件读取能力的 Agent（不做任何特殊设计），直接拿 12 题去测，检查题目有没有歧义、标准答案是不是真的唯一、判分标准写不写得清楚。这一步几乎不花开发成本，但能避免在一份有问题的考卷上白费力气去调 Agent。

**第 1 步：搭最简单版本，不接 MCP。**
用最朴素的两个工具函数（列目录、读文件），自己写的普通函数，不接协议。跑一遍 12 题，记录基线分数。

**第 2 步：把工具函数换成 MCP filesystem server，其他什么都不改。**
重新跑一遍 12 题。这一步只验证一件事：换协议本身有没有引入新问题。分数没掉，说明 MCP 这层接对了；分数掉了，问题出在协议接入，跟 Agent 的理解力/context 策略无关，容易定位。

**第 3 步：只有前两步跑完、且分数不够好，才加 context 管理机制。**
先从最朴素的纯文本笔记文件开始（NOTES.md 模式，不是数据库），只有真实观察到"笔记本身也大到读不过来了"或者"需要按关键词/语义去查笔记里的某一段"，才是引入 RAG/SQL 的时机——那时候会有具体证据支撑这个决定，不是现在凭直觉预判。
