# 读码机"迭代指路"模块 · 理论依据草案（v2 · 含用户凝练版）

> 核心问题：读码机凭什么给出一段代码的"迭代方向"？依据的第一性原理是什么？
> 对标：自动剧本生成机以亚里士多德《诗学》的 **want/obstacle 张力理论**为根基。
> 本文档为代码世界找到同构的"第一性原理"，v2 收入用户的凝练表述与"梯度"框架。

---

## 一、第一性原理（用户凝练版）

> 一个代码有两个相互牵扯的东西：
> - **行为（want）**：要实现的行为
> - **复杂度（obstacle）**：实现行为必须付出的代价
>
> 复杂度是 **bug 的来源、代码熵增的来源**；此外，行为的实现还可能因**偶然因素**（坏解法、过度设计）导致额外的熵增或 bug。
>
> **迭代的目标 = 两个方向：**
> 1. **在最小复杂度的情况下增加行为**
> 2. **单纯减少复杂度**

---

## 二、三处锐化（把刀刃磨利）

### 锐化 1：复杂度不是 bug 的"来源"，是 bug 的"温床"

更精确的因果链：

```
复杂度 ↑ → 人的心智模型装不下（记不住所有细节）
        → 现实（代码）与心智（以为的样子）出现落差
        → bug 住在落差里
```

复杂度像摩擦力：不直接弄坏东西，但摩擦力越大，滑手的概率越高。
**bug 不是复杂度"产生"的，是"复杂度让你 hold 不住，实现偏离了意图"产生的。**

### 锐化 2：两个方向之间，藏着"第零优先级"——消除落差

加行为、减复杂度之间，夹着一个**两边同时赢**的操作：

| 操作 | 行为 | 复杂度 | 效果 |
|---|---|---|---|
| 加行为 | ↑ | ↑（至少付本质复杂度） | 比值可能不变 |
| 减复杂度 | — | ↓ | 比值变大 |
| **消除落差**（死代码/缺陷/漂移） | ↑（行为兑现） | ↓（白付的复杂度收回） | **两边同时赢** |

最纯粹的例子是 **dead code**：它付了复杂度的"钱"，却没买到任何行为——**"付了钱没交货"的纯浪费**。删掉它，行为不变，复杂度下降。

**迭代优先级：第零步消除落差（免费赢）→ 然后才谈减复杂度、加行为。**

### 锐化 3："增加行为"只付本质复杂度，不付偶然复杂度

- **本质复杂度**（问题固有的）：必须付，是"必要的障碍"
- **偶然复杂度**（解法引入的）：一分都不该付
- 用户没要求的行为 = 本身就是偶然复杂度（过度设计 / YAGNI）——"买了没用上的复杂度"

---

## 三、最终公式与北极星问题

> **迭代 = 让「行为 / 复杂度」这个比值变大。**
>
> - 方向 A：行为 ↑，分母尽量不涨（只付本质复杂度）
> - 方向 B：分母 ↓，分子不变（减复杂度，尤其偶然复杂度）
> - 第零优先级：填落差（分子 ↑ 且分母 ↓，两头通吃）

**北极星问题**（判断任何迭代建议是否成立）：

> **"这个改动，会让下一个读代码/改代码的人，花更少的时间吗？"**
> 是 → 符合第一性原理；否 → 装饰性改动（甚至负债）。

## 四、读码机的识别逻辑（先定义、再判断）

### 4.1 行为（契约）怎么识别——信号来源

| 信号 | 来源 | 确定性 |
|---|---|---|
| 显性契约 | 函数/类名、docstring、类型签名、参数名 | 半确定（要看懂语义） |
| 隐性契约 | 调用方怎么用、期望什么输出 | 需分析调用关系 |
| 锁定契约 | **测试**锁定的行为（最可靠） | 确定 |
| 意图线索 | README、注释、commit message（git 历史） | 半确定 |

### 4.2 复杂度怎么识别——三层信号

| 层 | 信号 | 工具 |
|---|---|---|
| 结构性（确定性） | 嵌套深度、行数、圈复杂度、参数数量、重复代码块（AST）、魔法数字 | **AST + 度量工具**（pylint/radon），不靠模型 |
| 关系性（静态） | 耦合度、共享可变状态、依赖方向、import 数量 | 静态分析 |
| 语义性（LLM） | "这段代码为什么这么绕"、抽象是否恰当 | 大模型判断 |

### 4.3 落差（冲突）怎么识别

- dead code（定义了但没被调用）
- 注释/命名与实际行为不符
- 未处理的异常分支
- TODO/FIXME 永不兑现
- 实现与测试不一致

### 4.4 判断流程（感知 → 评估 → 决策）

```
读模块 → 提取(契约, 复杂度, 落差) → 打分（比值）→ 排序 → 输出迭代方向
         ↑ LLM 语义          ↑ 工具确定         ↑ 北极星问题校验
```

## 五、"梯度"框架（agent 的目标函数）

> **行为/复杂度 就是读码 Agent 的目标函数（价值函数）。**
> 它的"梯度"= 读码报告给出的方向：识别 → 打分 → 排序，指出**比值增长最快的方向**；
> 迭代建议 = **沿梯度方向的一步**。

### 与机器学习梯度的对应

| 机器学习 | 读码 Agent |
|---|---|
| 损失函数 | 复杂度/行为（比值倒数） |
| 梯度（方向） | 读码报告的"迭代方向" |
| 梯度下降的一步 | 一条迭代建议（重构/补测试/删死代码） |
| 学习率 | 改动幅度（小步重构 vs 大重构） |

### 两个必须标注的差异（诚实边界）

1. **这是"估计梯度"，不是"解析梯度"**：行为/复杂度不可精确计算（契约要理解、复杂度有主观成分），方向由 LLM 判断 + 工具度量合成——像**指南针**，方向可靠，精度有限。
2. **局部梯度 ≠ 全局最优**：沿局部梯度贪心走，可能陷入局部最优（无限重构、过度抽象）。需要**架构层全局视野**校准方向（类比：评估器不只算局部梯度，还看"地形图"）。

## 六、与剧本生成机的同构对照

| 剧本机 | 读码机 |
|---|---|
| 主线 = want × obstacle 张力 | 主线 = 契约 × 复杂度张力 |
| 角色 embody want/obstacle | 模块 embody contract/complexity |
| 场次大纲（sub_intents） | 模块分解（读码路线） |
| goal loop：生成→检查→诊断→修复 | 迭代指路：读→三问→诊断→给方向 |
| must_avoid 硬性约束 | 反模式/复杂度阈值（确定性工具验证） |
| 品味判断人工终审 | 架构品味同样人工终审 |

### 元原理（最深的洞察）

> **戏剧和代码共享同一个元原理——张力推动演化。**
> 戏剧的张力（want × obstacle）推动情节，代码的张力（契约 × 复杂度）推动迭代。
> 剧本机找"角色的张力"，读码机找"代码的张力"——同一套第一性原理的两个投影。

## 七、完整例子：给文章打分的函数

### 混乱版（契约藏在谜语里）

```python
def s(a):
    n = 0
    for w in a:
        if w in ['好', '棒', '赞']:
            n += 1
    return n * 2
```

- **want 模糊**：`s`/`a`/`n` 是什么？"n*2"为什么乘 2？→ 理解成本高
- **obstacle 明显**：魔法数字 2、魔法列表 → 修改成本高
- **落差**：没有测试锁定"每个积极词计 2 分" → 风险成本高

### 迭代方向（从张力推导）

1. **澄清契约**：改名 + docstring
2. **降低修改成本**：魔法值变常量
3. **锁定行为**：补测试

### 改进版

```python
POSITIVE_WORDS = ["好", "棒", "赞"]
POSITIVE_SCORE = 2

def score_article(words: list[str]) -> int:
    """按积极词数量给文章打分：每个积极词计 POSITIVE_SCORE 分"""
    positive_count = sum(1 for w in words if w in POSITIVE_WORDS)
    return positive_count * POSITIVE_SCORE
```

### 验证（北极星问题）

> 下一个来改的人（想把"真棒"加进词表）——旧版猜 5 分钟还不敢改；新版 5 秒定位、测试兜底。
> → 省时间了 = 符合第一性原理。✅

### 反例（不符合的"迭代"）

- 改名不改义（名字好听了，契约还是没人懂）
- 注释解释"是什么"但不降低"改的成本"
- 无测试兜底的大重构（反而增加风险成本）

## 八、诚实边界

1. 代码理论没有统一的《诗学》：Brooks/Lehman/SOLID 是经验定律，不是数学定理，但作指引框架足够
2. "迭代方向"给的是**改进假设**，要标置信度，重大问题留人工决策
3. 梯度是**估计的、局部的**：方向可靠，精度有限，需全局视野校准
