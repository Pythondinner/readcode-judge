# 当前功能参考

> 这份文档不按时间顺序写，只回答一个问题："读码机现在能做什么，怎么用"。
> 施工过程、每个决定的来龙去脉，去看 `工程日志/`；这里只留结果。
> 最后更新：2026-08-18（补充2.5：narrative判断的结构性盲区；补充2.7诊断建议；新增五、MCP接口）

## 一句话总览

读码机是两条能力线：**sensor**（读代码、回答问题）+ **judge**（给代码打体检、判断可信度、给出该关注什么）。它不写代码、不改代码、不自己决定要不要动手——只读，永远。

## 架构定位：对照 Ledger + Observer + Brain + Executor(+Analysis)

这是用户在多个项目里反复验证过的个人架构范式（自动剧本生成机的`brain.py`/`ledger.py`、diff_pr_Git的`brain/`/`ledger/`都是同一套范式的不同实例）：Ledger存状态、Observer看/发现/标记、Brain做决策、Executor动手执行，必要时加一层Analysis做深入诊断；可以组成状态机，也可以围绕一个goal形成自动化的goal_loop自迭代agent。

读码机对照这套范式，现在的定位是**只做Observer + Analysis这两块，Brain和Executor刻意不做**：

| 范式里的角色 | 读码机对应的部分 | 状态 |
|---|---|---|
| **Observer**（看、发现、标记） | judge层主体：复杂度→行为描述→项目叙述→行为判断→consensus→迭代信号 | 今晚系统性压力测试过，核心机制成熟 |
| **Analysis**（按需深入诊断） | `diagnose_and_propose_fix`——只在Observer标出具体发现后才启动 | 1样本5/5稳定，比Observer本身更可靠 |
| **Ledger**（存状态） | `eval_set/`+`工程日志/`是事实上的ledger，没有formalize | 未开始，下一个候选方向 |
| **Brain**（决策） | 无 | **刻意不做**——读什么、要不要修，由人或外部agent决定 |
| **Executor**（动手执行） | 无 | **刻意不做**——改代码永远走人工确认，这条边界今晚被真实验证过不止一次（`offer_to_write`那次假阳性被撤销） |

这不是"读码机还没做完"，是一个**有意识的架构决策**：这套范式里Brain+Executor在"代码判断"这个场景下必须由人把关，不该自动化——读码机的角色定死在Observer+Analysis，Brain+Executor留给外部有执行能力的agent（Claude Code/deepseek harness）或者人自己，通过MCP接口对接（见第五节）。

## 一、sensor：读代码、回答问题

```python
import agent
outcome = agent.answer_question(root, "你的问题")
# 或者走MCP协议：agent_mcp.answer_question(root, "你的问题")（异步）
```

- 会自己决定用`list_directory`/`search_code`/`read_file`（可选只读一段）去找答案，`final_answer`给结论。
- 连续重复失败会被检测到并提示换策略；MAX_STEPS=20（在7466文件的大仓库上验证过这个上限够用）。
- 想核实一个答案靠不靠谱：`verifier.verify_answer(root, question, answer)`，返回`verified: True/False/None`（`None`是"没查完"，不是"错了"）。

**规模**：验证过81MB/7466文件的真实开源仓库（deepseek-harness），也验证过多语言（Python走`complexity.py`/radon，JS/TS/Java/C/C++等走`lizard_complexity.py`/lizard）。

## 二、judge：给代码打体检

### 2.1 单文件/项目级复杂度+行为描述

```python
import report
file_report = report.generate_report(root, "某个文件.py")           # 单文件
project = report.generate_project_report(root)                      # 整个项目
```

- 复杂度（`complexity.py`用radon测Python，`lizard_complexity.py`用lizard测其它语言，两者验证过在Python上100%数字一致）只是**入场券**——只对B级以上的函数才跑下面这步。
- 只有过了入场券的函数，才会调`behavior.py`生成契约描述（输入/输出/副作用/前置条件/调用后保证/【调用方须知】），再用`verifier.py`独立核实，标`verified: True/False/None`。
- `format_report(file_report)` / `format_project_report(project)` 转成Markdown。

### 2.2 项目叙述：行为该拿什么当标准

```python
project = report.generate_project_report(root, with_narrative=True)
# project["narrative"]：项目定位+关键不变量，已核实
# project["judged_behaviors"]：每个函数 support/undermine/unclear
```

- 单独生成：`report.describe_project(root)`——不是营销summary，是列出具体、可核对的项目不变量（状态机规则、硬性约束、数据不丢失规则等）。
- 单独判断一个函数：`report.judge_behavior_against_narrative(narrative, function_info, description)`。
- **`verifier.py`默认的核实步数上限（4步）是为单函数场景校准的，项目叙述这种要核对十几条跨文件说法的场景要传`max_steps`覆盖**（`describe_project`内部已经传了15）。
- **`describe_project(root, verbose, explore_max_steps, verify_max_steps)`支持按次覆盖探索/核实步数预算**（不传就用各自默认值20/15），大项目该显式调大——`agent.answer_question`本身也支持`max_steps`参数，不再是硬编码常量。
- **规模限制，已用真实数据验证**（工程日志31）：49文件86函数的真实模块测试，即使把探索预算翻倍（40步），叙述也只能覆盖一部分文件，导致57%的函数"无法判断"——不变量数量不会随文件数等比例增长。**大项目上"0违反"不能读成"干净"，要读成"这次机制只对能覆盖到的那部分函数给出了判断"**。分子包多次生成叙述、分别判断，是可能的缓解方向，还没验证过。

### 2.3 可靠性：单次判断不能直接信

- 实测：19个函数的行为判断，跑5次独立判断，**74%完全一致，26%不稳定**——包括唯一确认的真实bug本身（`write_and_save_one_with_check`）也只有60%一致率。
- `judge_project_against_narrative_consensus(project_report, narrative, runs=5)`——固定材料不变，跑N次，统计一致率。
- `synthesize_project_report_consensus`——同样的思路用在"跨函数模式归纳+优先清单"（`synthesize_project_report`）上。
- **这套机制测的是随机噪音，不是系统性偏差**——如果模型对某类风险的判断本身有偏，跑几次都会一致地得出同一个错误结论，高一致率不等于判断对了。目前没有测量系统性偏差的手段。

### 2.4 迭代信号：不是一个分数，是分层

```python
signal = report.build_iteration_signal(project_report, judgment_consensus, min_agreement=0.6)
report.format_iteration_signal(signal)
```

- **Tier 1**：consensus核实、一致率≥门槛的功能违反——复杂度不参与这一层。
- **Tier 1'**：出现过违反投票但没到门槛的——不是"没问题"，是"这次判断本身靠不住，需要人工核实"。
- **Tier 2**：功能层面没疑虑的函数，复杂度才单独起作用，指向"可维护性该往哪投入"，不代表优先级。
- 不合并成加权分数——功能是离散判断，复杂度是连续量，硬凑是范畴错误；而且两者可靠性不是一个量级（复杂度零噪音，行为判断26%噪音）。

### 2.5 已知的结构性盲区（永久边界，不是待办）

narrative锚定判断（2.2/2.3）的范围明确是"这段行为符不符合项目级契约"——**不是通用bug检测器**，这条边界现在有真实证据支撑，不是猜测：

- **真实撞见过的漏判**：`brain.py::process_turn`一个真实bug（状态被拒时数据没有跟着回退，用户已确立内容被静默清空），consensus 5次全部一致判"support"——不是26%那种随机噪音，是**方法论范围外的盲区**：这类"函数自己的局部控制流有没有自洽"的问题，跟项目级叙述完全无关，narrative判断天然看不到。
- **两次补救尝试都不成立**：①给判断层加"局部自洽性"判断——测试发现这个能力不需要建，一个没有任何脚手架的裸review agent一次就抓到了，判断层没有必要再造一遍；②把判断拆成"适用性+满足性"两步——真跑出来发现引入了新的、更隐蔽的失败模式（循环论证：拿"这个函数没有确认机制"反推"这条规则跟它无关"），比原来的问题更糟，已放弃。
- **该怎么用**：需要检查局部逻辑自洽性时，跑一次独立的、不带narrative材料的裸review（人工或调用一个不做特殊准备的agent），结果跟narrative判断的结果**并列看，不合并成一个verdict**——两种检查的盲区不重叠，合并只会互相掩盖。

### 2.6 改动前后对比

```python
before = report.judge_project_against_narrative_consensus(project_report, narrative)
# ...改代码...
after = report.judge_project_against_narrative_consensus(project_report, narrative)
report.compare_judgment_consensus(before, after)
```

- 纯数据比较，不调API。使用方式是工作纪律（必须在改代码前主动跑一次留底），不是自动生效的追踪系统。
- 明确不做：翻git历史自动分析旧版本代码（需要对旧版本重新生成叙述和行为描述，成本跳一个量级）。
- **真实验证过一次完整闭环**（工程日志22）：`write_and_save_one_with_check`从undermine（60%一致率）→人诊断+修复→support（100%一致率），`compare_judgment_consensus`正确识别出变化。流程是人工执行每一步（判断→诊断→改代码→跑pytest→git提交→重新判断），不是一键自动化，但机制上证明了"发现问题→真的改好→复核确认"这条链能走通。

### 2.7 诊断+修复建议

```python
d = report.diagnose_and_propose_fix(root, file_path, function_name, matched_invariant, reasoning, description)
# {"diagnosis", "agent_steps", "agent_hit_cap", "verified", "verify_evidence", "verify_reasoning"}
```

- 针对Tier1里一条"违反不变量"的发现，主动去找这个函数的**实际调用方**（判断层现有环节全部只看被标记的函数自己，看不到调用图）——判断这个问题在真实调用路径下会不会被触发、该怎么修。只产出诊断文字，不写文件、不改代码。
- 是agentic任务（复用`agent.answer_question`），不是像判断层那样"材料已经齐了，一次性推理"——调用方是谁要现查，不是提前能喂进prompt的静态材料。
- **可靠性已实测**（工程日志27）：对同一个已知答案的真实发现跑5次，5/5得出同一个结论、5/5独立找到同一条调用链、5次verifier全部核实通过——比判断层本身（同一问题60%一致率）更稳。只在1个函数、1种"有明确调用链可查"的问题类型上测过，样本小，不能类推到所有情况（比如更偏局部逻辑判断类的诊断，稳定性还没测）。

## 三、明确不做的边界

| 边界 | 状态 |
|---|---|
| 自动改代码（executor层） | 100%不做。改代码永远是人工审批下的协作（今晚的真实先例：读码机产出判断→人核实调用路径→人审批→动手改），不是读码机自己长出执行能力 |
| 持续自动追踪（动态追踪原计划） | 不做——确定性趋势追踪已被CodeScene等成熟工具覆盖，语义判断层的噪音水平也不支持高频自动对比 |
| 长期记忆/历史积累 | 没有——每次运行都是一次性的，没有跨会话持久化的判断历史库 |
| 系统性偏差检测 | 没有手段——consensus只测噪音；跨模型交叉核对已验证是无解的猜疑链（换个模型只是把"信不信"这个问题挪了个地方，没有独立于任何模型的真值可以核对），不作为解决方案 |
| 局部控制流自洽性检测（narrative判断覆盖不到的一类真实盲区） | 不建新机制——已验证裸review agent免费具备这个能力，且尝试把它并进narrative判断（两步拆分）会引入循环论证这类新失败模式。定为工作纪律：需要时跑独立裸review，跟narrative判断结果并列看，不合并 |
| 压缩/笔记机制 | 没有证据支撑需要，未做 |

## 四、语言支持

| 语言 | 复杂度 | 行为描述/判断 |
|---|---|---|
| Python | `complexity.py`（radon），精确 | 支持 |
| TS/JS/Java/C/C++/C#/Go/Rust/Kotlin/Swift/Ruby/PHP/Scala等 | `lizard_complexity.py`（lizard），验证过跟radon在Python上100%一致 | 支持（机制本身语言无关） |
| 其它 | 不支持，`tool: None`，报告如实说明 | — |

`search_code`（sensor层）目前不覆盖`.tsx`等少数扩展名——已知但未验证有实际影响的缺口。

## 五、MCP接口：给外部agent当信号源

```bash
READCODE_ROOT=/path/to/target/repo python src/judge_mcp_server.py
```

通过stdio协议启动，暴露两个工具（跟sensor层的`mcp_server.py`是同一种包装方式，只是暴露judge层更高层的能力）：

- `generate_project_report_tool(with_narrative=True)`——跑一遍完整体检，返回排版好的Markdown报告。
- `diagnose_and_propose_fix_tool(file_path, function_name, matched_invariant, reasoning, description)`——针对报告里一条具体发现，深入查调用方、给最小化修复建议。

只产出报告和建议文字，不写文件、不改代码——执行永远是外部agent自己的事，读码机不越界。

**已验证**：写了独立的MCP client测试脚本，两个工具都通过真实MCP协议调用成功（工程日志29）。撞见并修好一个此前没被发现的问题：`mcp_server.py`（sensor层那个，更早建的）的`import`本身是错的（`mcp.server.mcpserver.MCPServer`在当前SDK版本里不存在，应为`mcp.server.fastmcp.FastMCP`）——说明它可能从未真的作为独立进程被成功启动过，这次是第一次真的用子进程方式测才暴露出来。

**还没做的**：只测过协议本身通不通，没有接一个真的有执行能力的agent（Claude Code/deepseek harness）走一遍"看报告→挑发现→拿建议→人工确认→改代码"的完整路径；consensus和迭代信号分层（Tier1/Tier2）还没接进MCP，只挑了报告生成和诊断这两个最直接有用的工具。
