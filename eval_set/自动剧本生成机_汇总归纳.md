## 跨函数模式归纳

基于已核实的契约描述，我识别出以下跨函数模式：

### 模式1：静默覆盖/持久化未经验证的数据（高风险）

**支撑证据**：
- `writer.py :: write_and_save_one`：不校验 `project_state` 是否为 `confirmed` 就生成并持久化草稿，且静默覆盖 `_meta.generated_from[mode]` 旧值（第270-274行）。
- `goal_loop.py :: write_and_save_one_with_check`：即使 `status == "cap_reached"`（未通过检查），仍无条件调用 `ledger.save_draft` 保存有缺陷的草稿（第296行）。
- `brain.py :: process_turn`：原地修改并返回传入的 `snapshot`，`_meta` 下的 `flagged_injection`、`flagged_snippets`、`conflicts_flagged` 被模型返回结果整体覆盖（第204-206行），且非法状态被静默改写为 `"collecting"`。

**归纳**：多个核心写入路径都倾向于"先落盘再说"，缺乏对数据质量的前置校验或失败回滚机制。调用方难以从函数名或返回值判断数据是否真正可用。

---

### 模式2：副作用远超函数名/文档暗示（隐蔽性高）

**支撑证据**：
- `chat.py :: offer_to_write`：删除最新草稿时连带清空运行事实清单（`_clear_run_facts`），该副作用仅在 `ledger.delete_draft` 的 docstring 中提及。
- `ledger.py :: _migrate_chain_to_series`：即使对独立项目调用，也会改变其磁盘路径（从扁平变为嵌套），并非"仅确保已嵌套"。
- `chat.py :: maybe_link_predecessor`：成功承接时不仅创建新项目，还可能迁移整条链的目录结构（`shutil.move`）。
- `server.py :: continue_from`：成功创建会触发整条链的物理迁移，改变其他项目的磁盘路径。

**归纳**：多个函数在完成主要任务的同时，会触发额外的文件系统变更或数据清理，这些副作用在函数名和常规文档中不可见，调用方极易遗漏。

---

### 模式3：确认/重试机制的不对称性（调用方需两步操作）

**支撑证据**：
- `server.py :: write_draft`：已有草稿且未带 `force` 时返回 `needs_confirmation` 分支，调用方必须实现两步确认流程才能真正覆盖旧草稿。
- `server.py :: continue_from`：`force` 为假且已有后继时返回 200（`needs_confirmation: True`）而非错误码，调用方必须检查该字段。
- `goal_loop.py :: write_with_check`：重试过程中加固的 `must_avoid`/`must_include` 措辞是临时的，不会体现在返回的 snapshot 中，但 `sub_intents` 的修改会持久化。

**归纳**：多个函数采用"先确认、后执行"的两步模式，但确认分支的返回格式不统一（有的返回特殊字段，有的返回错误码），且确认后真正执行时的行为（如 `write_and_save_one_with_check` 即使未通过也保存）可能与调用方预期不符。

---

### 模式4：环境变量加载的"不覆盖"语义（配置陷阱）

**支撑证据**：
- `chat.py :: load_env`：使用 `os.environ.setdefault`，已存在的环境变量不会被 `.env` 覆盖。
- `server.py :: load_env`：与 `chat.py` 中的 `load_env` 行为完全一致（第18-25行），同样使用 `setdefault`。

**归纳**：两个入口模块（chat.py 和 server.py）各自实现了 `load_env`，且都采用"不覆盖"语义。调用方若期望 `.env` 覆盖已有配置，会得到静默的相反结果。

---

## 优先处理清单

### 第1优先：`goal_loop.py :: write_and_save_one_with_check`（复杂度7，但风险最高）

**理由**：该函数在 `status == "cap_reached"` 时仍无条件保存有缺陷的草稿（第296行），这是**静默持久化错误数据**的问题。相比复杂度更高的 `offer_to_write`（复杂度27）和 `write_with_check`（复杂度26），这个函数的风险在于：调用方（如 `chat.py` 或 `server.py`）可能基于"未通过就不落盘"的假设，实际却得到一份有问题的草稿被持久化，且后续 `latest_draft` 会返回这份缺陷内容，污染整个创作链。这是数据完整性问题，优先级最高。

### 第2优先：`chat.py :: offer_to_write`（复杂度27）

**理由**：虽然复杂度最高，但更关键的是它是一个**无限循环**，在非交互环境（自动化脚本）中调用会挂起；且删除最新草稿时连带清空运行事实清单的副作用完全不可见。这两个问题叠加，使得该函数在自动化集成场景下既可能阻塞进程，又可能静默破坏数据。复杂度高 + 隐蔽副作用 + 阻塞风险，应优先重构（如增加超时参数、将副作用显式化）。

### 第3优先：`writer.py :: write_and_save_one`（复杂度6）

**理由**：不校验 `confirmed` 状态就生成并持久化草稿，且静默覆盖 `generated_from`。虽然复杂度不高，但它是 `chat.py` 和 `server.py` 共用的底层写入函数，调用方若未做前置校验（如 `server.py :: write_draft` 做了校验，但 `chat.py :: offer_to_write` 未做），会直接产生未确认的草稿落盘。修复成本低（增加状态校验），收益高（防止错误数据进入持久层）。

### 第4优先：`ledger.py :: _migrate_chain_to_series`（复杂度9）

**理由**：物理移动磁盘目录的副作用影响面大——不仅影响当前项目，还影响整条链的所有项目路径。`server.py :: continue_from` 和 `chat.py :: maybe_link_predecessor` 都依赖它，调用方若缓存了旧路径会失效。虽然复杂度不高，但属于"低复杂度、高影响面"的典型，应优先补充文档或改为显式调用。

### 第5优先：`deepseek_client.py :: call`（复杂度11）

**理由**：`json_mode=True` 时内部最多发送 3 次请求（含重试），调用方只看到一次调用但账单是多次的；缺 API key 时抛 `SystemExit` 而非 `ApiCallError`，调用方若只捕获后者会漏掉。这是所有 LLM 调用的底层入口，影响面最广，但风险相对可控（不涉及数据持久化），故排在数据完整性类问题之后。
