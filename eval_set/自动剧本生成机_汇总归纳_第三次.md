## 跨函数模式归纳

### 模式 1：静默覆盖/持久化未经验证的数据，且副作用在函数名和 docstring 中不可见

**支撑证据（4个函数）：**
- `writer.py :: write_and_save_one`：不校验 `project_state` 是否为 `confirmed` 就生成并持久化草稿（docstring 明确"这里不做校验"），且静默覆盖 `_meta.generated_from[mode]` 旧值。
- `goal_loop.py :: write_and_save_one_with_check`：即使 `status == "cap_reached"`（重试封顶未通过检查），仍无条件调用 `ledger.save_draft` 保存有缺陷的草稿。
- `brain.py :: process_turn`：原地修改并返回传入的 `snapshot`，`_meta.flagged_injection`、`flagged_snippets`、`conflicts_flagged` 被模型返回结果整体覆盖（调用方持有的旧引用被静默替换）。
- `chat.py :: offer_to_write`：删除最新版本草稿时连带清空运行事实清单（`_clear_run_facts`），该副作用在函数名和 docstring 中完全看不出来。

**归纳**：多个函数倾向于在调用方不知情的情况下，将未经验证或未经确认的数据持久化/覆盖到已有状态中，且这些副作用往往隐藏在函数名和 docstring 之外，调用方难以从接口签名预判。

---

### 模式 2：调用方需自行检查返回值中的"确认/未完成"标记，否则会误判操作结果

**支撑证据（3个函数）：**
- `server.py :: write_draft`：已有草稿且未带 `force=true` 时返回 `needs_confirmation: True`（200），不生成任何内容——调用方若不检查该字段会误以为生成成功。
- `server.py :: continue_from`：predecessor 已有后继且 `force` 为假时返回 `needs_confirmation: True`（200）而非错误码——调用方必须检查该字段，否则误以为创建成功。
- `goal_loop.py :: write_with_check`：返回的 `snapshot` 中 `sub_intents` 可能已被悄悄改写（有意的持久化修复），但 `must_avoid`/`must_include` 的加固措辞只是临时的、不会体现在返回的 snapshot 中——调用方若误以为返回 snapshot 里带着加固措辞会判断错误。

**归纳**：多个函数在"需要确认/未完成"时返回 200 或正常返回值，而非错误码或明确标记，调用方必须主动检查特定字段（`needs_confirmation`、`sub_intent_changes` 等）才能识别真实状态，否则会误判操作结果。

---

### 模式 3：磁盘路径/文件系统布局会被隐式改变，调用方缓存路径会失效

**支撑证据（3个函数）：**
- `ledger.py :: _migrate_chain_to_series`：即使链上只有根节点一个成员，也会把它从 `ledger/<root>/` 搬进 `ledger/<root>/<root>/`——对一个从未被续写过的独立项目调用它也会改变磁盘路径。
- `server.py :: continue_from`：成功创建会触发整条链的物理迁移（`os.rename`），把 predecessor 所在链的所有项目从扁平目录移到系列子目录，改变其他项目的磁盘路径。
- `chat.py :: maybe_link_predecessor`：成功承接时通过 `ledger.create_continuation` 创建新项目，并可能把整条链迁移进新的系列文件夹（`shutil.move`），改变磁盘目录结构。

**归纳**：多个函数在"创建承接/续写"场景下会触发整条链的物理迁移，改变磁盘目录结构，调用方若缓存了旧路径会失效；且这些迁移副作用在函数名中不可见（如 `maybe_link_predecessor` 看起来像"询问"）。

---

### 模式 4：LLM API 调用次数与调用方感知不一致，可能产生显著延迟和费用

**支撑证据（3个函数）：**
- `deepseek_client.py :: call`：`json_mode=True` 时内部最多重试 2 次，同一个 `call` 调用可能实际向 API 发送最多 3 次请求——调用方只看到一次调用，但账单和延迟是多次的。
- `goal_loop.py :: check_and_report`：为每条违反的 must_avoid 条目发起一次独立的 LLM 调用（`diagnose` 内部调用 `deepseek_client.call`），must_avoid 列表较长时会产生多次外部 API 调用。
- `goal_loop.py :: write_with_check`：每次尝试后若发现问题会调用 `diagnose`/`repair_sub_intent` 发起额外 LLM 调用，重试机制（默认最多 3 次）叠加诊断修复，实际 API 调用次数远超调用方感知的单次生成。

**归纳**：多个函数在内部隐式发起多次 LLM API 调用（重试、诊断、JSON 解析重试），调用方只感知到一次调用，但实际 token 消耗和延迟是多次的，在手动模式或批量场景下可能带来显著成本。

---

### 模式 5：环境变量加载使用 `setdefault` 语义，已有值不会被覆盖

**支撑证据（2个函数）：**
- `chat.py :: load_env`：使用 `os.environ.setdefault`，已存在的环境变量不会被 `.env` 文件覆盖。
- `server.py :: load_env`：同样使用 `os.environ.setdefault`，语义与 chat.py 版本一致。

**归纳**：两个入口模块（chat.py 和 server.py）各自实现了 `load_env`，且都使用 `setdefault` 语义——如果调用方在调用前已设置同名环境变量，`.env` 文件中的值会被静默忽略，可能导致配置与预期不符。

## 优先处理清单

### 优先级 1：`goal_loop.py :: write_and_save_one_with_check`（复杂度 7，B 级）

**理由**：虽然复杂度不高，但它在 `status == "cap_reached"`（重试封顶未通过检查）时**无条件保存有缺陷的草稿**——这是数据完整性问题，会导致有问题的正文被持久化到 ledger，后续所有依赖该草稿的流程（如续写、展示）都会基于错误数据。且该行为在函数名和 docstring 中不可见，调用方无法预判。这比一个复杂度高但风险可控的函数更该优先处理。

### 优先级 2：`brain.py :: process_turn`（复杂度 13，C 级）

**理由**：原地修改并返回传入的 `snapshot`，且 `_meta` 下的 `flagged_injection`、`flagged_snippets`、`conflicts_flagged` 被整体覆盖——如果调用方在别处持有这些字段的旧引用或依赖其历史值，会被静默替换。同时状态被静默改写为 `"collecting"` 时调用方若不检查返回值会误以为状态转移成功。这是核心对话循环的入口，影响面广。

### 优先级 3：`server.py :: write_draft`（复杂度 9，B 级）

**理由**：已有草稿且未带 `force=true` 时返回 `needs_confirmation: True`（200）而非错误码——调用方（前端）若不检查该字段会误以为生成成功，实际什么都没写。这是 HTTP API 的对外契约，影响所有通过 API 使用系统的调用方，且两步确认流程容易被忽略。

### 优先级 4：`ledger.py :: _migrate_chain_to_series`（复杂度 9，B 级）

**理由**：对一个从未被续写过的独立项目调用它也会改变磁盘路径（从扁平变成嵌套）——这是文件系统级别的副作用，调用方若只期望"查询系列根"而误用此函数会意外改动文件系统布局。且该迁移会连锁影响 `list_projects()` 返回的名字列表（同一系列会同时出现多个名字），调用方若拿这些名字做去重或路径拼接会出错。

### 优先级 5：`deepseek_client.py :: call`（复杂度 11，C 级）

**理由**：`json_mode=True` 时内部最多重试 2 次，同一个 `call` 调用可能实际向 API 发送最多 3 次请求——调用方只看到一次调用，但账单和延迟是多次的。这是所有 LLM 调用的底层入口，影响所有上层函数的成本和延迟。同时缺 `DEEPSEEK_API_KEY` 时抛 `SystemExit`（不是 `ApiCallError`），调用方若只捕获 `ApiCallError` 会漏掉这个退出，进程直接终止。
