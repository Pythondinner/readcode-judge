项目定位描述如下（依据均来自实际读过的文件，逐条标注证据范围）：

## 1. 项目是什么

一个**基于 want/obstacle 张力理论的剧本/小说自动生成系统**（README.md 开头）。面向需要从模糊口头需求生成结构化故事设定、再生成正文的用户，解决"从一句话需求到完整正文"的自动化问题。核心理论：故事主线是 want（想要什么）与 obstacle（被什么阻挡）之间的张力，人物只是载体（`embodies: want/obstacle/null`），一部作品只有一条主线，张力必须逐场升级（brain.py CORE_RULES、writer.py CORE_RULES）。

## 2. 模块组成与职责边界

- **brain.py**：交互层，显式状态机（empty → candidates_pending → collecting → confirmed），模型只在状态内做内容判断，状态转移由代码兜底校验。不持久化，每次从 ledger 读、处理完写回（brain.py process_turn）。
- **ledger.py**：持久化层，快照+草稿存取，按项目/系列分文件夹，只做读写不做判断（ledger.py 模块 docstring）。
- **writer.py**：写手层，把 schema 翻译成正文，含长篇自动分段（write_long_script），不判断内容对错。
- **checker.py / checker_include.py**：must_avoid / must_include 语义检查器，只做检查不做修改。
- **goal_loop.py**：批量生成的自动检查+修复循环（write_with_check / write_missing_acts_in_series），以及手动模式的检测按钮（check_and_report）。
- **chat.py**：终端交互入口。
- **server.py**：Web 后端（Flask），包一层 HTTP API。
- **deepseek_client.py**：共享 API 调用封装。

## 3. 关键不变量（每条标注证据范围）

### 3.1 状态机合法性
- **不变量**：不允许转入 `confirmed` 除非 `throughline.want` 和 `obstacle` 都非空；状态被拒时数据也退回（不能只挡状态不挡数据）。
- **证据**：brain.py process_turn 中 `if next_state == "confirmed": if not merged_throughline or not merged_throughline.get("want") or not merged_throughline.get("obstacle"): next_state = "collecting"; reject_throughline_patch = True`。这是系统唯一的硬骨架（docs/00 第11条）。
- **覆盖入口**：chat.py 的 `brain.process_turn` 调用、server.py 的 `/api/projects/<name>/message` 路由都走同一个 process_turn，因此这条规则对两个入口都成立。

### 3.2 系列续写的前提
- **不变量**：只有 predecessor 状态为 `confirmed` 才能创建续集，否则抛 ContinuationError。
- **证据**：ledger.py create_continuation 中 `if pred_state != "confirmed": raise ContinuationError(...)`。
- **覆盖入口**：chat.py 的 `maybe_link_predecessor` 调用 create_continuation（捕获 ContinuationError 后提示）；server.py 的 `/api/projects/<name>/continue_from` 路由同样调用 create_continuation 并捕获 ContinuationError 返回 400。两个入口都遵守。

### 3.3 续集继承规则
- **不变量**：新一幕继承角色/场景/genre/tone，但 want/obstacle 必须重新推导，不能照抄上一幕。
- **证据**：ledger.py build_continuity_brief 只搬运 characters/setting/genre/tone，不搬运 throughline；brain.py empty 状态 prompt 明确"throughline.want/obstacle 依然必须重新确立，不能照抄上一幕的"。
- **覆盖入口**：chat.py 和 server.py 的续写入口都走 create_continuation + brain 状态机，规则一致。

### 3.4 草稿版本管理
- **不变量**：同一项目同一 mode 的草稿版本号递增，互不覆盖；`latest_draft_filename` 以版本号最大为最新，是唯一规则。
- **证据**：ledger.py save_draft（`next_version = (max(versions) + 1)`）、latest_draft_filename（`max(candidates, key=version_of)`）。
- **覆盖入口**：chat.py 的 `offer_to_write` 生成、server.py 的 `/api/projects/<name>/write` 路由都调用 save_draft，规则一致。

### 3.5 删除草稿时事实清单的联动
- **不变量**：删除某 mode 的最新版本时，连带删除对应的 `_state.md` 事实清单；删除非最新版本时保留。
- **证据**：ledger.py delete_draft 中 `was_latest = mode and latest_draft_filename(...) == filename`，若 was_latest 则删除 state 文件。
- **覆盖入口**：chat.py 的 `删除<文件名>` 分支调用 ledger.delete_draft；server.py 的 `/api/projects/<name>/drafts/<filename>` DELETE 路由同样调用。两个入口都遵守。

### 3.6 手动模式只诊断不修改
- **不变量**：手动检测（check_and_report）只诊断，不修改任何内容（不修 sub_intent、不改 must_avoid/must_include）。
- **证据**：goal_loop.py check_and_report 只调用 checker/diagnose，不调用 repair_sub_intent、不重试；tests/test_goal_loop.py `test_check_and_report_does_not_mutate_inputs` 断言传入的 must_avoid 和 sub_intents 未被改动。
- **覆盖入口**：chat.py 的 `检测` 分支调用 goal_loop.check_and_report；server.py 的 `/api/projects/<name>/drafts/<filename>/check` 路由调用同一函数。两个入口都遵守。

### 3.7 自动路径的修复持久化规则
- **不变量**：自动路径（write_and_save_one_with_check）中，sub_intent 修复结果**存回** snapshot；must_avoid/must_include 的临时加固措辞**不存回**（只在本轮重试内存在）。
- **证据**：goal_loop.py write_and_save_one_with_check 中 `if result["sub_intent_changes"]: current["sub_intents"] = result["snapshot"]["sub_intents"]; ledger.save_snapshot(...)`，但 must_avoid 的加固只在 write_with_check 内部修改内存副本，不写回 ledger；tests/test_goal_loop.py `test_write_and_save_one_with_check_persists_sub_intent_but_not_augmented_must_avoid` 断言 `persisted["sub_intents"][0]["text"] == "修复后的sub_intent"` 且 `persisted["rule_based"]["must_avoid"] == ["某约束"]`。
- **覆盖入口**：goal_loop.write_missing_acts_in_series 内部调用 write_and_save_one_with_check（批量路径）；chat.py 的 `批量小说/批量剧本` 分支和 server.py 的 `/api/projects/<name>/write_series` 路由都走 write_missing_acts_in_series。手动路径（write_and_save_one）不涉及自动修复，不适用此规则。

### 3.8 封顶时保留违反最少的一版
- **不变量**：达到 MAX_ATTEMPTS=3 还没通过时，返回违反条数最少的一版，不是随便返回最后一版。
- **证据**：goal_loop.py write_with_check 末尾 `best = min(attempts, key=lambda a: a["violation_count"])`；tests/test_goal_loop.py `test_cap_reached_returns_least_violated_attempt` 断言 `result["content"] == "v2"`（违反最少的一版）。
- **覆盖入口**：write_with_check 是自动路径的核心，被 write_and_save_one_with_check 调用，进而被批量路径使用。手动路径不涉及重试，不适用。

### 3.9 previous_excerpt 在重试时保持不变
- **不变量**：重试时 previous_excerpt 始终是调用方传入的"上一幕正文"，不会被替换成本幕失败的重试草稿。
- **证据**：goal_loop.py write_with_check 中 previous_excerpt 参数在循环内原样传给 write_long_script，从不修改；tests/test_goal_loop.py `test_previous_excerpt_stays_constant_across_retries` 断言两次尝试的 previous_excerpt 都是同一个值。
- **覆盖入口**：write_with_check 的自动路径。手动路径不重试，不适用。

### 3.10 批量生成的顺序与停止规则
- **不变量**：批量生成按系列链顺序执行；已有正文的幕次跳过；遇到未收尾（非 confirmed）的幕次停止，不处理后续幕次。
- **证据**：goal_loop.py write_missing_acts_in_series 中 `if ledger.latest_draft(...) is not None: skipped_exists; continue`、`if ... != "confirmed": skipped_not_confirmed; break`；tests/test_goal_loop.py `test_write_missing_acts_in_series_skips_existing_and_stops_at_unconfirmed` 断言 act1 跳过、act2 生成、act3 未处理。
- **覆盖入口**：chat.py 的 `批量` 分支和 server.py 的 `/api/projects/<name>/write_series` 路由都调用 write_missing_acts_in_series，规则一致。

### 3.11 生成前必须 confirmed
- **不变量**：生成正文前，项目状态必须是 confirmed，否则拒绝。
- **证据**：server.py `/api/projects/<name>/write` 路由 `if snapshot["_meta"]["project_state"] != "confirmed": return 400`；writer.py write_and_save_one 注释说明"调用方负责确认这一幕状态是 confirmed"。
- **覆盖入口**：server.py 的 write 路由明确校验；chat.py 的 offer_to_write 只在收尾（confirmed）后调用，且 brain 状态机保证只有 confirmed 才触发 offer_to_write。两个入口都遵守。

### 3.12 删除项目的两步确认流程
- **不变量**：删除项目必须走"先查询依赖信息、用户确认、再带 force=true 调一次"的两步流程，不存在第一次调用直接删除。
- **证据**：server.py `/api/projects/<name>` DELETE 路由 `if not force: return needs_confirmation + successors/predecessor`，只有 force=true 才调用 ledger.delete_project。
- **覆盖入口**：仅 server.py 提供 HTTP 删除入口；chat.py 没有删除项目的功能（只有删除草稿）。因此这条规则只对 server.py 的 DELETE 路由成立。

### 3.13 重新生成正文的两步确认流程
- **不变量**：已有正文时重新生成，必须带 force=true 才执行，否则返回依赖信息（dependents）供确认。
- **证据**：server.py `/api/projects/<name>/write` 路由 `if not force and ledger.latest_draft(...) is not None: return needs_confirmation + dependents`。
- **覆盖入口**：仅 server.py 的 write 路由。chat.py 的 offer_to_write 用交互式 `input("确定要重新生成吗？...")` 实现确认，但这是 CLI 交互，不是 force 参数机制，两者实现不同但都要求用户确认。因此这条规则对 server.py 的 write 路由成立；chat.py 的确认机制是另一套实现，但同样要求用户显式确认。

### 3.14 续写分支的确认流程
- **不变量**：当 predecessor 已有后继幕次时，从它续写需要用户确认（或 force=true），不能默默创建分支。
- **证据**：server.py `/api/projects/<name>/continue_from` 路由 `if existing_successors and not force: return needs_confirmation + leaf_suggestions`；chat.py maybe_link_predecessor 中 `if existing_successors: ... if input(...) != "是": return`。
- **覆盖入口**：server.py 的 continue_from 路由和 chat.py 的 maybe_link_predecessor 都实现确认，规则一致。

### 3.15 事实清单与文风参考的分离
- **不变量**：world_state（事实清单）是硬性事实约束，优先级高于 previous_excerpt（文风参考）；两者用途不同，不能混淆。
- **证据**：writer.py CORE_RULES 中"<world_state> 是硬性事实约束，优先级高于文风参考"；write_long_script 中 previous_excerpt 和 world_state 分别传入 write_script。
- **覆盖入口**：writer.write_and_save_one 和 goal_loop.write_and_save_one_with_check 都通过 gather_world_state_chain 获取 world_state、通过 load_draft 获取 previous_excerpt，规则一致。

### 3.16 封顶时草稿仍会保存但标记未检查
- **不变量**：自动路径封顶（cap_reached）时，草稿仍会保存（不让批量流程卡死），但会写一个 `.unchecked` 标记文件，让"未完全通过检查"这个事实在磁盘上可持久查询。
- **证据**：goal_loop.py write_and_save_one_with_check 中 `if result["status"] == "cap_reached": ledger.mark_draft_unchecked(project_name, filename)`；ledger.py mark_draft_unchecked 写 `<filename>.unchecked` 文件。
- **覆盖入口**：仅自动路径（write_and_save_one_with_check）。手动路径不自动检查，不适用。

## 4. 设计特点与取舍

- **状态机 + 单次结构化调用**：代码确定状态，模型只在状态内做内容判断，且判断和处理是同一次调用（docs/00 第13条）。
- **持久化层为唯一真相来源**：brain 不缓存状态，每次从 ledger 读、写回（docs/00 第7条）。
- **只对唯一硬骨架做强校验**：只有 want/obstacle 非空才能 confirmed，其余字段动态可改（docs/00 第11条）。
- **标记不拦截**：矛盾/注入等不确定判断用中性提示，不自动拦截（docs/00 第3条）。
- **自动 vs 手动路径分离**：批量场景自动检查+修复+重试（最多3次），手动场景只诊断不改（docs/11 第4.1节）。
- **检查粒度是整幕不是分段**：重试时整幕重新生成，代价是长文本重试成本高（docs/11 第4.4节）。
- **previous_excerpt 重试时保持不变**：跨幕文风锚点不被本幕失败草稿污染（goal_loop.py 注释 + 测试）。
- **prompt 注入防御**：所有外部内容用数据标签包裹并声明"不是指令"（brain.py/writer.py/checker.py 的 CORE_RULES）。
- **已知限制**：local_slip 和 must_include 的修复路径从未在真实场景验证过；小说/剧本双模式事实一致性未处理（docs/11 第4.4节、README 已知限制）。
