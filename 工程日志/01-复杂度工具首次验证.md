# 复杂度工具首次验证

> 2026-08-17

## 做了什么

装了`radon`，写了`src/complexity.py`——对一个`.py`文件跑AST分析，输出每个函数/类的圈复杂度、字母评级（radon内置的A-F标准）、所在行号，按复杂度从高到低排好序。完全不经过大模型，纯工具调用。

## 真实测试结果

**`agent.py`**（读码机自己的核心循环，73行，我熟悉）：
```
[B] answer_question（第63行）复杂度=10
[A] repeat_notice（第42行）复杂度=1
```

**`goal_loop.py`**（自动剧本生成机的goal loop，351行，更复杂）：
```
[D] write_with_check（第124行）复杂度=26
[B] check_and_report（第228行）复杂度=10
[B] write_and_save_one_with_check（第263行）复杂度=7
[A] write_missing_acts_in_series（第321行）复杂度=5
[A] diagnose / repair_sub_intent / _augment_must_avoid / _augment_must_include 复杂度=1
```

## 结果对不对得上直觉——对得上，而且很准

- `agent.py`的`answer_question`是真正的核心循环（for循环+多条if/elif分支），`repeat_notice`只是纯格式化字符串，没有任何分支——工具给出的10 vs 1，跟这个直觉判断完全一致。
- `goal_loop.py`里`write_with_check`复杂度26、评级D，是全文件唯一一个复杂度这么高的——**这个结果准确对应了我今晚反复读写这个文件时的真实感受**：这个函数确实是全文件里逻辑最纠缠的一个（嵌套循环+诊断分支+两种修复路径），不是错觉，工具量化出来的排序和我自己的主观感受第一次真正对上了。
- 其余几个小函数（`diagnose`/`repair_sub_intent`这类，本质是包一层模型调用+格式化）复杂度都是1，符合"这些函数很单薄、没什么可判断的分支"这个预期。

## 初步结论

第一次真实验证：**复杂度这一侧的工具化是可信的，不需要靠模型去"估"，直接用radon这类AST工具算出来的数字，跟真实的主观复杂度感受一致**。这条腿站得住，接下来可以放心往上叠"行为描述"那一侧，不用再回头怀疑复杂度这个基础数据可不可靠。

## 补测（同一天）：再测4个文件巩固信心

追加测了`ledger.py`（31个函数，样本量最大的一次）、`writer.py`、`brain.py`、`checker.py`，五个文件加起来覆盖了约40个函数。结果：

- `ledger.py`最高分是`_migrate_chain_to_series`（9分，B级）——负责把扁平存储迁移成系列嵌套目录，中间有临时路径倒手、多次存在性检查，是这个文件里公认最绕的一个函数。
- `writer.py`最高分是`write_long_script`（13分，C级）——分段循环+滚动事实清单窗口+异常处理+条件拼接，全文件最复杂的函数。
- `brain.py`最高分是`process_turn`（13分，C级）——结构校验+patch合并+多字段更新，全文件最复杂的函数。
- `checker.py`只有一个函数，2分，符合"这个文件本来就很单薄"的预期。

**五个文件、约40个函数，每一次"复杂度最高"的判断都精确对应了我自己对这几个代码库的真实理解，零意外。** 这不是巧合——不同文件、不同代码风格（有的函数多而分散如ledger.py，有的函数少而集中如writer.py），工具给出的排序都站得住，说明这不是偶然测中一次，是真的可靠。

## 还没做的

- 还没测过"复杂度工具会不会在某些写法上给出反直觉的分数"这类边界情况（比如大量简单if-elif平铺 vs 真正嵌套很深的逻辑，圈复杂度算法本身对这两种情况的区分度够不够）——五次测试都没撞见这类反例，暂不专门去构造，等真遇到了再处理。
- 还没跟"行为描述"这一侧接起来——现在只是一个独立能跑的工具，还没有整合进`agent.py`的判断流程或者做成一份完整的"模块体检报告"。
