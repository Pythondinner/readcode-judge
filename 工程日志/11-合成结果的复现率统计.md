# 合成结果的复现率统计：consensus机制

> 2026-08-17

## 背景

上一篇工程日志（10）发现两次汇总合成给出的优先级排序不完全一致，只有第1名稳定。用户看完后提议：既然"刑事阅卷Agent"项目的`consensus.py`就是解决"同一份材料独立跑多次、合并时标注复现次数"这个问题的，直接把这个机制正式做出来，不要只停留在"猜测第1名可信、其余不可信"。

## 做了什么

先把`synthesize_project_report`的返回值从一段格式随意的文本，改成结构化的JSON（`{"patterns": [...], "priority_list": [...]}`，用`json_mode=True`）——不这么改的话，没法程序化比较多次独立调用的结果，只能靠人工重新读一遍文本去对比，那不是真的"统计"。

新增`synthesize_project_report_consensus(project_report, runs=5, top_n=5)`：对同一份project_report独立跑N次合成，只对"优先处理清单"做程序化统计（结构清晰，是`{file, function}`这种能直接算复现次数的东西）；"跨函数模式"的措辞每次不完全一样，不好机械合并，原样保留每一轮的结果供人工比对，没有强行去重/合并成一份"标准答案"——跟阅卷Agent的`consensus.py`处理的问题不完全一样（那边是"同一份材料单次处理可能漏内容"，这边是"材料完整但判断本身有波动"），只借鉴"多次跑、标复现次数"这个思路，不照搬对方的具体合并逻辑。

## 真实结果（自动剧本生成机，19条材料，跑5次，各取前5名）

| 函数 | 复现率 | 平均排名 |
|---|---|---|
| `goal_loop.py::write_and_save_one_with_check` | 100%（5/5） | 1.8 |
| `chat.py::offer_to_write` | 80%（4/5） | 1.0 |
| `ledger.py::_migrate_chain_to_series` | 80%（4/5） | 3.8 |
| `writer.py::write_and_save_one` | 60%（3/5） | 3.3 |
| `server.py::continue_from` | 60%（3/5） | 4.3 |
| `deepseek_client.py::call` | 60%（3/5） | 4.7 |
| `brain.py::process_turn` | 40%（2/5） | 3.5 |
| `server.py::write_draft` | 20%（1/5） | 3.0 |

## 这次统计推翻了什么、确认了什么

- **确认**：`write_and_save_one_with_check`（"未通过检查也静默保存有缺陷草稿"）5次全中，是唯一一个真正稳定的第一优先级，之前两次单独跑就已经看出这个信号，这次量化后更有底气。
- **推翻/纠正**：工程日志10记录的第二次单独合成里，`server.py::write_draft`排进了优先级第4——**这次5次统计显示它只出现过1次（20%复现率），本质是噪音，不该被当成一个稳定结论**。反过来，`_migrate_chain_to_series`在两次单独跑里排名忽高忽低（一次没进前5，一次进了第4），但5次统计下来复现率高达80%，比它任何一次单独出现时的排名都更值得信——**单次结果的"有没有出现"和"排第几"，都不能直接当结论，复现率才是更可信的信号**。
- `offer_to_write`很有意思：只有80%复现率（不是100%），但一旦出现，几乎总是排第1（平均排名1.0）——这跟`write_and_save_one_with_check`的"稳定但不是最靠前"形成对比，提示"复现率"和"排名"是两个独立的维度，都要看，不能只看一个。

## 结论

- consensus机制本身跑通了，而且第一次真实运行就推翻了一个之前基于单次结果得出的错误印象（`write_draft`的"优先级第4"）——这不是假设性的价值，是这次真实统计出来的。
- 代价是显而易见的：5次独立合成调用，比一次贵5倍。这次是在已经有完整的19条材料基础上做的，材料本身不用重新生成——如果连材料生成本身也要跑5次（比如怀疑behavior.py的描述本身不稳定），成本会高得多，目前没有证据表明需要这么做，先不做。

## 还没做的

- "跨函数模式"（不是优先级清单）本身没有做复现率统计，只是原样并列展示5轮的结果供人读——模式的名字、措辞、归类方式每次都不完全一样，没有设计出一个可靠的程序化比对方法（比如"两个模式算不算同一个模式"这个判断本身还是模糊的），这次刻意没有强行解决这个更难的问题。
- 只在一个9文件的项目上跑过一次consensus，跑5次要花的时间/成本没有系统测量，只有这一次的观察。
