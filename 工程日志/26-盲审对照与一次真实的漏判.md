# 盲审对照测试，撞见judge层一次真实的、非噪音的漏判

> 2026-08-18

## 起因

用户问：读码机/信号机做的事，是不是Claude Code或deepseek harness自带的能力就已经覆盖了，我们在重复造轮子？

没有靠推理回答，而是设计了一个真实对照测试：把自动剧本生成机拉回基线提交（`b335176`，`write_and_save_one_with_check`的cap_reached bug还在），起一个完全不知道judge层、不知道narrative、不知道具体哪个函数的全新agent，让它像"请review这份代码"一样盲审一遍——模拟Claude Code原生review能力在没有任何自定义脚手架时会做的事。

## 结果：两种方法互相漏判，不是互相覆盖

盲审agent**完全没找到**`cap_reached`那个bug（judge层找到的，自己也只有60%一致率）——这类"违反项目级契约"的问题，没有narrative锚定确实抓不住。

但它**找到了一个judge层完全没找到的、真实存在的新bug**，就在`brain.py::process_turn`——这个函数在此前的consensus测量里是**5次独立运行全部判"support"**（工程日志19数据），我自己在做跨模型分歧核查时也独立读过这段代码、同样判断"support没问题"（见更早的对话记录）。两边都错了。

真实bug：

```python
if next_state == "confirmed":
    if not merged_throughline or not merged_throughline.get("want") or not merged_throughline.get("obstacle"):
        next_state = "collecting"  # 注释说"退回上一个合理状态"
...
for key in ("rule_based", "throughline", ...):
    if key in patch:
        snapshot[key] = patch[key]   # 但这里无条件合并，throughline没被排除
```

状态守卫只挡住了`next_state`不让进`confirmed`，但没挡住数据——无效的throughline（`want`/`obstacle`为空）依然被合并进`snapshot`并存盘，用户已确立的内容被静默清空，没有任何提示。跟`goal_loop.py`那次cap_reached bug是同一个"结果被部分丢弃"的家族，但发生在完全不同的文件、不同的具体机制里。

## 为什么judge层的narrative判断会漏掉这个

narrative判断问的是"这个函数的行为支不支撑项目级的整体约定"——这类问题对"某个具体分支的局部意图有没有被代码完整执行"这种细粒度的自洽性问题天然不敏感，因为项目叙述根本不会（也不应该）细到"拒绝确认时throughline patch要不要一起丢弃"这个实现层面的颗粒度。这不是随机噪音（5/5一致，不是consensus能测出来的那种不稳定），是judge层现有方法结构性覆盖不到的一类问题。

## 修复与验证

`src/brain.py`：状态被拒时新增`reject_throughline_patch`标记，合并循环里同步跳过throughline这个key，让数据回退跟状态回退保持一致（commit `23430d5`）。

验证方式：brain.py没有任何现成pytest覆盖（盲审agent自己也指出了这点），所以手写了before/after对照复现脚本，用mock模型输出制造"确认被拒"的场景，确认修复前bug精确复现、修复后数据正确保留；同时跑了现有22个pytest确认没有连带破坏；重新生成process_turn的契约描述并重新判断，描述已经准确写出"该轮throughline patch被丢弃"，判断结果support（这次是对的）。

## 结论：该做什么

不是继续攒更多跨模型对照样本（上一轮已经想清楚这条路的回报有限），而是给"缩窄判断范围"这个已经定好的优先级找到了一个具体、有真实证据支撑的方向：**narrative-vs-behavior判断和"函数自身控制流有没有自洽"是两个不同粒度的问题，前者不该也不能替代后者**。后者不需要项目叙述做material，只需要函数自己的源码——形状更接近checker.py式的窄问题（"这个分支声明的意图，后面的代码有没有完整做到"），而不是宽泛的语义判断，理论上更便宜、更少受narrative覆盖不到的盲区影响。

## 还没做的

- 这个"局部控制流自洽性"检查目前只是个方向，还没有真的写成一个独立的、可复用的判断任务去试跑（比如喂给模型：只给这一个函数的源码，不给项目叙述，问"每个分支声明的意图有没有被后续代码完整执行"），也没有测过它会不会有自己的新盲区或者新的误报率。
- 只验证了它能不能补上这一次的漏判，没有拿去回测其他已知的真实bug（cap_reached、offer_to_write的确认不对称），看这类"局部自洽性"检查能不能覆盖更多。
