# 第一次真实完整闭环：dsh版

> 2026-08-19

## 背景

今天前半段一直卡在Claude Code的登录问题上（OAuth error、401、最后查到根因是`~/.claude/settings.json`里一份意外遗留的第三方代理配置+环境变量冲突，已经修好，但没来得及重新验证完整闭环）。用户提出"先适配dsh，跑个闭环测试看看效果"——放弃当晚继续死磕Claude Code登录，转而给`dialogue.py`接一条新的执行者路径。

## dsh的真实情况（跟最初设想有落差，如实记）

- dsh（deepseek-harness）默认只自带两个profile：`web`和`headless`，**没有现成的、类似Claude Code那种交互式终端UI**——`--profile tui`只是文档里演示"怎么装第三方社区插件"的例子，不是内置功能。
- `headless`模式不交互、直接执行，真实测过还撞见过5分钟无响应，不适合"先确认再执行"的设计要求。
- Python SDK的完整agentic能力（真正读写文件+跑bash）**明确不支持Windows**（"the persistent PTY backend requires a POSIX terminal substrate"），直接排除。
- 最终只剩`web`模式可行——文档确认它有原生确认机制（"The Web UI asks before operations that require approval"），符合"读码机不自己实现确认机制"这条一直坚持的原则。
- 挖过一次dsh内部的Typert RPC框架，想看能不能程序化把任务塞进web session——是它前后端通信用的内部机制，不是留给外部调用的公开接口，继续深挖投入产出比不划算，放弃这个方向。
- 顺带查过一次网上关于dsh的资料，发现搜出来的大部分站点是SEO内容农场（工具6天前才发布开发者预览版，这么快冒出一堆"完整指南"是可疑信号），不采信，继续以本地仓库自带文档为准。

## 实现

`dialogue.py`新增`_invoke_deepseek_harness`+`--executor=dsh`参数：起`dsh web`服务（`subprocess.Popen`，不是`run`，因为是常驻服务）、轮询等真的能拿到HTTP响应才开浏览器（不是固定睡几秒——第一次撞过"睡5秒不够、浏览器打开时服务还没起来"，第二次撞过"裸测TCP端口能连上不代表HTTP服务真的能处理请求"，两次真实bug都改过了，现在是真的发HTTP请求确认）、打印诊断文本等用户手动复制粘贴进dsh对话框、确认dsh处理完之后关掉服务。

跟Claude Code那条路径的关键差异：Claude Code是终端交接，全自动；dsh是"半自动"——起服务、开浏览器是自动的，但"把任务发给dsh"这一步需要用户手动复制粘贴，是明确的、已知的缺口，不是忘了做。

## 便宜的测试样本

原本用来测试的`剧本机_测试用_有bug版本`（真实项目worktree）跑一次读码机分析成本高、耗时长，用户提出想要更便宜的测试目标。新建`读码机_dsh快速测试样本`：两个极简文件，真实复现`--test-handoff`固定诊断材料描述的同一类bug（`write_and_save_one_with_check`对`cap_reached`状态不做区分、无条件保存），跑之前手动验证过bug真实存在，用git管理方便测完`git checkout -- .`恢复初始状态重复测试。

## 结果：第一次真实完整闭环

`--test-handoff --executor=dsh`真实跑通全程：

1. 报告生成→诊断文本→确认交给dsh
2. dsh web服务真实启动（第一次npx要下载包，实测启动很慢，轮询等待生效）
3. **dsh真的读了代码、复现了bug、按诊断建议的思路（额外落一个`.unchecked`标记文件，正文不悄悄丢掉）修复、写验证脚本跑了4个场景全部通过、清理了临时产物**——过程和结论写得很扎实，还主动指出"诊断里的行号对应原始项目，这个样本是按函数名映射的复现"这种细节，没有被字面数字带偏
4. `_compare_before_after`自动重新分析，真实检测到复杂度变化：`write_and_save_one_with_check`从1→2（新增分支判断），新出现`_mark_unchecked`（复杂度2）——两条都跟dsh真实做的改动完全对得上

## 如实记录的局限，不要美化

这次"判断结果没有变化"**不是**narrative判断层确认了修复有效——是因为改动前后都是"0个函数触发判断"，这个测试样本复杂度太低，没有一个函数够到narrative判断的门槛，判断层这次根本没被真正exercise到。这次验证的是**交接机制+复杂度层面的改动检测**都是真实有效的，但没有验证"判断层能不能正确识别出undermine变成support"——之前三次手动闭环（cap_reached、throughline、offer_to_write）都验证过这一层，这次因为样本太简单没触发到。是这次为省成本选极简样本的天然代价，不是缺陷，需要留着下次用一个复杂度够高的样本补测。
