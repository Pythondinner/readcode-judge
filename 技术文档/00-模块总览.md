# 模块总览

> 这份文档讲"现在的代码具体是怎么运作的"，是技术细节，不是设计决策的由来——决策为什么这么定，去 [../docs/01-讨论中的思维闪光点.md](../docs/01-讨论中的思维闪光点.md) 看。
> 对应代码版本：读码机 step1（无 MCP 版本）
> 最后更新：2026-08-15

## 1. 现在有哪几个文件，各自管什么

```
src/
  deepseek_client.py   共享的模型调用封装（从自动剧本生成机原样复制过来，通用，不用改）
  tools.py             agent能用的两个动作：列目录、读文件，划定了能碰的路径范围
  agent.py             核心循环：一步步决定读什么、什么时候给出最终答案
  run_eval.py           跑起步考卷的12题，把每题的过程和答案记下来
eval_set/
  起步考卷.json         12道题 + 标准答案 + 判分说明
  step1_结果.json        run_eval.py跑完之后产出的，agent对每题的实际回答
```

三个源文件的依赖关系很简单，是一条线，不是网状：

```
run_eval.py
   │  读取 eval_set/起步考卷.json 里的每一道题
   ▼
agent.py（answer_question函数）
   │  每一步决定"我要不要读文件、读哪个"
   ▼
tools.py（list_directory / read_file）
   │  真正去碰文件系统，返回文件内容或目录列表
   ▼
deepseek_client.py（call函数）
   在agent.py和tools.py之间来回——每一步都要调一次模型问"接下来干嘛"
```

## 2. 一道题从提出到回答，具体发生了什么（完整时序）

用第7题"为什么write_missing_acts_in_series要从writer.py挪到goal_loop.py"举例：

1. `run_eval.py`从`起步考卷.json`里读到这道题的文字，调用`agent.answer_question(root, 这道题)`。
2. `agent.py`内部维护一个叫`transcript`的字符串变量，一开始只有题目本身："\<question\>为什么...\</question\>\n\n（还没有做任何操作。）"。
3. 第1轮：把`transcript`整个喂给模型（连同`SYSTEM_PROMPT`），模型看到"还没做任何操作"，大概率决定先`list_directory`看看代码库里有哪些文件。
4. `agent.py`收到模型返回的JSON（`{"action": "list_directory", "path": ""}`），调用`tools.list_directory(root, "")`，拿到文件名列表（`brain.py`、`ledger.py`……）。
5. 把这一步"做了什么、看到了什么"拼接进`transcript`，进入第2轮。
6. 第2轮：模型看到文件列表里有`goal_loop.py`（题目问的函数名跟这个文件相关），决定`read_file`读它。
7. 拿到`goal_loop.py`的完整内容后同样拼进`transcript`，进入第3轮。
8. 模型在读到的内容里发现函数确实在`goal_loop.py`里，但题目问的是"为什么从writer.py挪过来"——它可能还需要去读`writer.py`确认那边有没有留下相关的注释，于是继续`read_file("writer.py")`。
9. 读到`writer.py`末尾那段解释"为什么挪走"的注释后，模型认为信息够了，输出`{"action": "final_answer", "answer": "……循环import……"}`。
10. `agent.py`识别到`final_answer`，循环结束，把答案连同"一共走了几步"返回给`run_eval.py`。
11. `run_eval.py`把这道题的（题目、标准答案、agent的答案、走了几步）存进`step1_结果.json`。

**这个过程里没有任何一步是"代码在理解语义"**——每一步"读哪个文件、要不要继续"的判断，全部是模型自己做的；`agent.py`只负责执行模型说的动作、把结果原样喂回去，是一个纯粹的"传话+执行"循环，不掺杂任何自己的判断逻辑。

## 3. 跟"真正的" Agent 框架/MCP 版本比，现在这版少了什么

对照组是以后要做的 MCP 版本（读码机 step2），现在这版刻意做得很简陋，方便看清楚最原始的样子：

| | 现在（step1） | 以后（step2，接MCP） |
|---|---|---|
| 工具怎么定义 | `tools.py`里两个普通Python函数 | 遵循MCP协议的标准接口，任何MCP客户端都能调，不是agent专属的 |
| 模型怎么知道能用什么工具 | 写死在`SYSTEM_PROMPT`的文字里 | 由MCP协议在运行时告诉模型有哪些工具、参数是什么，不用手写进prompt |
| 对话历史怎么维护 | 一个不断变长的字符串（`transcript`） | 同样的问题依然存在，MCP不解决这个，属于下一层要考虑的事 |

第2步接MCP，唯一该变的应该只是"工具怎么定义、怎么调用"这一层，`agent.py`里"要不要继续读、什么时候给答案"这个判断逻辑不应该因为换了协议而改变——如果换了MCP之后连这部分逻辑都要重写，说明现在这版的设计耦合得太紧，是需要在step2里检查的地方。
