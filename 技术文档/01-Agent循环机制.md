# Agent 循环机制详解

> 专门讲 `agent.py` 这一个文件——它是整个读码机最核心的部分，多花点篇幅讲清楚。
> 最后更新：2026-08-15

## 1. 核心设计：用一段不断变长的文本代替"对话历史"

很多讲 Agent 的资料会提到"messages 数组"——把每一轮的角色（user/assistant/tool）和内容存成一个列表，发给模型时把整个列表传过去。**这一版故意没有用这种结构**，原因是：

1. `deepseek_client.py`（从`自动剧本生成机`原样搬过来的）现在只支持"一个 system_prompt + 一个 user_content"，不支持传一个多轮消息列表——如果要用 messages 数组，得先去改这个共享模块，而这个模块在另一个项目里还在用，不想因为这边的需求把它改复杂。
2. 更重要的原因：**用一段纯文本表示"目前为止发生的事"，比消息数组更容易看懂、也更容易调试**——你可以把`transcript`变量在任何一步打印出来，看到的就是一段完整的、人能读的记录，不需要理解"role: assistant"这种结构化格式背后代表什么。对算法基础还在打底的阶段，这种"眼见为实"的调试方式价值更大。

具体做法：`agent.py`里的`transcript`变量，从"只有题目"开始，每一轮把"模型说了要做什么"和"实际做完之后看到了什么"都追加进去，下一轮把这个变长之后的完整字符串再喂给模型。模型每一轮看到的，都是从最开始到现在**完整的历史**，不是只看当前这一条。

## 2. 循环的四种可能结果，逐个拆开看

```python
for step_num in range(1, MAX_STEPS + 1):
    result = deepseek_client.call(SYSTEM_PROMPT, transcript, ..., json_mode=True)
    action = result.get("action")

    if action == "final_answer":
        ...  # 结果1：正常结束，返回答案
    elif action == "list_directory":
        ...  # 结果2：执行动作，继续循环
    elif action == "read_file":
        ...  # 结果3：执行动作，继续循环
    else:
        observation = f"（未识别的action：{action!r}，请重新按格式输出）"  # 结果4：模型输出格式不对
```

**结果4很容易被忽略，但很重要**：`json_mode=True`只保证模型输出的是合法JSON，不保证`action`字段的值一定是我们认识的三个词之一——模型完全可能输出`{"action": "search_file"}`这种我们没定义过的动作（比如它"以为"应该有这个功能）。这里的处理方式是**不报错、不中断整个循环**，而是把"你这个动作我不认识"作为一次正常的"观察结果"喂回去，让模型自己在下一轮纠正——这是从`goal_loop.py`里"标记不拦截"那条思路搬过来的，出了意外不是让整个程序崩掉，是把意外本身变成给模型的下一条信息。

## 3. MAX_STEPS 硬上限：为什么是8，为什么一定要有

```python
MAX_STEPS = 8  # 硬上限，避免agent在读文件这件事上无限循环
```

如果没有这个上限，理论上模型可能会陷入"读了A文件，觉得不够，又去读B文件，又觉得不够……"一直循环下去，尤其是遇到它答不上来的问题时，更容易出现这种情况（因为它"想找到答案"，但可能根本找不到）。`goal_loop.py`里的`MAX_ATTEMPTS = 3`是同一个思路——**这个上限的作用是兜底，不是因为我们预期正常情况下需要走满8步**（起步考卷12题按人工估计，最多问的问题也就需要读2-3个文件，5步以内应该能搞定，8是留了一些余量）。到达上限还没给出`final_answer`，`agent.py`会返回一个"超过最大步数未能得出答案"的结果，而不是让程序卡死或者报错退出——这跟`write_with_check`到达`MAX_ATTEMPTS`时"返回违反条数最少的一版"是同一种"安全阀独立于判断准不准"的设计。

## 4. Temperature 为什么设成 0.2

```python
result = deepseek_client.call(SYSTEM_PROMPT, transcript, temperature=0.2, json_mode=True)
```

这不是随便定的数字，是复用了`自动剧本生成机`里已经验证过的一个判断标准：**需要"稳定、可重复"的任务用低温度，需要"有变化、有创造力"的任务用高温度**。`checker.py`的语义判断用的是`temperature=0`（要求"同一个输入多问几次答案基本一致"），`writer.py`的正文生成用的是`0.9`（创作任务需要变化）。读码机这里"决定下一步读哪个文件、要不要给答案"更接近判断任务，不是创作任务，所以用低温度——`0.2`而不是`0`，是留了一点点余地（万一某一步卡住需要一点随机性去尝试不同路径），但整体偏保守。这个数字目前是按经验定的，还没有专门调过，如果后续发现"同一道题多跑几次答案差异很大"，第一个该怀疑的参数就是这里。
