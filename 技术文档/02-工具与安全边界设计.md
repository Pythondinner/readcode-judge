# 工具与安全边界设计

> 专门讲 `tools.py`——只有两个函数，但里面有一个不明显、容易漏掉的安全考虑。
> 最后更新：2026-08-15

## 1. 两个工具函数本身很简单

```python
def list_directory(root: str, rel_path: str = "") -> str: ...
def read_file(root: str, rel_path: str) -> str: ...
```

就是`os.listdir`和`open().read()`的简单包装，没有任何智能判断——给什么路径就列/读什么路径，理不理解内容是模型的事，`tools.py`只负责"照做"。

## 2. 真正的设计点：`_resolve`函数做的路径边界检查

```python
def _resolve(root: str, rel_path: str) -> str:
    rel_path = (rel_path or "").strip().lstrip("/\\")
    full = os.path.normpath(os.path.join(root, rel_path))
    root_abs = os.path.normpath(root)
    if not (full == root_abs or full.startswith(root_abs + os.sep)):
        raise ValueError(f"路径 {rel_path!r} 超出了代码库根目录范围，拒绝访问")
    return full
```

这段代码要解决的问题：**如果模型（不管是故意的，还是"跑偏了"）在`path`字段里给了类似`"../../其他文件夹/.env"`这种带`..`的路径，会不会读到代码库根目录以外的文件？**

不做这道检查的话，`os.path.join(root, "../../.env")`会真的拼出一个跳出`root`范围的路径，`read_file`会老老实实把它读出来——`.env`这种文件里存着API key，如果不小心被读出来又被模型写进了某次回答里，是真实的信息泄漏风险，不是危言耸听。

**这道检查具体怎么做的**：把`root`和用户给的`rel_path`拼起来、用`os.path.normpath`标准化（把`..`这类相对路径符号解析掉，比如`a/../b`会变成`b`），再检查算出来的绝对路径是不是**真的**落在`root`目录内部（要么完全等于`root`本身，要么以`root + 路径分隔符`开头）。如果不是，直接拒绝，返回一句解释，而不是抛出异常让整个程序崩掉——跟`agent.py`里"未识别的action"的处理方式是同一个思路，把"拒绝"本身也变成一次正常的观察结果反馈给模型。

## 3. 这道检查目前保护的范围有多大，别高估

**现在这版只挡了"读到根目录外的文件"这一种风险**，没有做的事情包括：

- 没有限制单次能读的文件大小——如果代码库里混进一个几十MB的大文件，`read_file`会原样读完整个内容塞进`transcript`，可能直接把上下文撑爆。现在`自动剧本生成机/src`都是几百行的小文件，还没撞到这个问题，但换成大代码库测试时大概率会撞上——这个问题目前故意没有处理，等它真的发生了再说（对应设计文档里"复杂机制要等真实瓶颈出现再上"那条原则，这里反过来是"简单的防护措施也不用提前做全，缺口先记下来"）。
- 没有防"读的文件数量太多"——理论上模型可以在`MAX_STEPS`允许的范围内把整个代码库都读一遍，`tools.py`不会阻止这种行为，靠的是`agent.py`的步数上限间接兜底，不是`tools.py`自己在管这件事。
- 只挡了"往外读"，没有做"防止读到不该读的内部文件"这类更细的权限控制（比如以后如果代码库里有`.env`，即使在root内部，可能也不希望被这个agent读到）——现在没做这层，因为目标代码库`自动剧本生成机/src`本身不含敏感文件，暂时不需要。

这份清单不是待办事项，是**明确写下来"现在保护到哪一步为止"，避免以后忘了这些边界条件，误以为`tools.py`比它实际做到的更安全**。
