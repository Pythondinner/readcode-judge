# 评测数据格式

> 讲两份 JSON 数据的结构——考卷本身，和跑完之后产出的结果。
> 最后更新：2026-08-15

## 1. `eval_set/起步考卷.json`——考卷本身

```json
{
  "target_codebase": "考卷是针对哪个代码库出的",
  "note": "为什么标准答案能在agent写出来之前就先定好",
  "tiers": { "四个难度层级各自的说明": "..." },
  "questions": [
    {
      "id": 1,
      "tier": "属于哪个难度层级",
      "question": "题目原文",
      "answer": "标准答案",
      "grading": "这道题该怎么判分（精确匹配，还是看关键点有没有提到）"
    }
  ]
}
```

**`grading`字段现在只是文字说明，还没有变成能自动执行的判分逻辑**——目前的判分方式是人工把`agent_answer`和`standard_answer`放在一起读，凭这段说明去判断对不对（就是这次跟你一起做的事）。以后如果要做成自动判分脚本，第1/2/4档（精确匹配类）比较容易写代码判断，第3档（语义判断类）大概率要再调一次模型去做"这个回答有没有提到关键论点"这种判断——判分本身也是一次模型调用，不是一段纯规则代码。

## 2. `eval_set/step1_结果.json`——`run_eval.py`跑完的产出

```json
[
  {
    "id": 1,
    "tier": "1_单文件事实题",
    "question": "题目原文",
    "standard_answer": "标准答案（从考卷里带过来的，方便对照，不用来回翻两个文件）",
    "agent_answer": "agent实际给出的回答",
    "steps_taken": 2,
    "hit_cap": false
  }
]
```

`steps_taken`和`hit_cap`这两个字段现在看起来没什么用（这次12题全对，`hit_cap`全是`false`），但留着是有意义的——**以后对比"加了笔记机制之后，是不是同样的题步数变少了"，或者"某一类题是不是特别容易撞到步数上限"，都得靠这两个字段的历史数据积累**，不是现在就用得上，是提前把这个记录习惯定下来，跟`自动剧本生成机`的`chapter_reports`记录"这一段是不是被截断了"是同一个"顺手记下来，以后可能用得上"的思路。

## 3. 两份数据文件目前是分开的，故意没有合并

`起步考卷.json`是"人写的、不会因为agent表现而改变"的东西；`step1_结果.json`是"agent跑出来的、每次跑可能都不一样"的东西——保持两个文件分开，一是避免不小心把agent的输出覆盖掉人工维护的标准答案，二是以后如果要跑`step2_结果.json`（接了MCP之后再跑一遍），能很清楚地对比"标准答案没变，但不同版本的结果文件在变"，而不是在同一份文件里又要维护标准答案又要维护每次运行的输出，容易搞混。
