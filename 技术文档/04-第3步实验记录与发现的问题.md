# 第3步实验记录与发现的问题

> 目标代码库从 `自动剧本生成机`（9文件、单层目录、用户本人熟悉）换成了 Flask 真实源码（24文件、约9200行、三层目录、用户和出题人都不是Flask核心开发者，但出题人——我——实际读了源码再写标准答案，不是凭印象编的）。
> 最后更新：2026-08-15

## 1. 结果概览

| | step1（无MCP） | step2（MCP） |
|---|---|---|
| 得分 | 9/10 | 9/10 |
| 唯一答错的题 | 第9题 | 第9题 |
| 失败方式 | 撞上 MAX_STEPS=8，未给出答案 | 撞上 MAX_STEPS=8，未给出答案 |
| 其余9题 | 全对，步数3-7步不等 | 全对，步数3-6步不等 |

**两版在同一题上以完全相同的方式失败，其余题目结果一致**——这再次确认了第2步的结论：MCP协议本身不是问题所在，两版agent在"读懂代码"这件事上表现完全对等，问题出在协议之外的地方。

## 2. 第9题失败的完整过程

题目："flask/json/这个子目录下有哪几个.py文件？"

两版都做了同一件事：连续8次调用`list_directory("flask/json")`，每次都收到"（flask/json 不是一个目录，或者不存在）"这条报错，一次都没有换过参数，最后撞上步数上限，返回"超过最大步数，未能得出答案"。

## 3. 根因排查：先看是不是出题错了

目标代码库的根目录（`ROOT`）本身已经是`C:\FPAN\Python312\Lib\site-packages\flask`，也就是说`tools.py`/`mcp_server.py`里"相对代码库根目录的路径"这个说法里，**根目录已经是flask文件夹本身，不是它的上一级**。要访问`flask/json/`这个子目录，正确的相对路径应该是`"json"`，不是`"flask/json"`——后者会被解析成`ROOT + "flask/json"`，也就是`.../flask/flask/json`，这个路径当然不存在。

**这是出题时的失误**：题目文字里写"flask/json/这个子目录"，是站在"整个flask包"的视角描述路径（类似`import flask.json`那种写法），但没有对应到工具调用时"相对代码库根目录"这个具体含义上——这个疏漏是人（出题人）造成的，不是agent的判断力问题。

## 4. 排查到出题失误之后，更值得深挖的问题：agent面对失败为什么不换策略

如果只停在"这是我出题的锅"，会漏掉一个更值得记录的真实缺陷。换个角度想：**就算题目本身有歧义，一个足够聪明的agent，在收到6-7次同样的"路径不存在"报错之后，也应该有能力自己意识到"这个路径可能是错的，换个思路试试"**——比如尝试单独用`"json"`当路径，或者退回去重新`list_directory("")`看看根目录下实际有哪些东西。两版agent都没有做到这一点，是完全相同的、机械的重复。

**根源在`agent.py`（以及`agent_mcp.py`）现在的循环设计里**：一个动作失败之后，处理方式只有一句——

```python
transcript += f"\n\n=== 第{step_num}步 ===\n你的动作：{...}\n观察结果：{observation}"
```

**只是把报错原样拼回transcript，没有任何"这已经是第几次失败了、要不要换个方式"的判断逻辑**，完全指望模型自己从"历史记录里有好几条一样的报错"这个信号里领悟到该换策略——这次的真实结果证明，光靠这样"隐式地把失败摆在那里"是不够的，模型没有主动去做这个反思。

**这跟`goal_loop.py`里"诊断失败原因、不盲目重试"的原则是同一件事**，只是这次踩坑的是`agent.py`自己，不是`goal_loop.py`——`goal_loop.py`面对写手违反约束，会先诊断是`structural_conflict`还是`local_slip`，再针对性修复，不会让写手带着同样的错误无脑重写三次；但`agent.py`面对"这个路径读不到"，现在没有对应的诊断步骤，纯粹指望模型自己开窍。

## 5. 安全阀验证：至少没有失控

值得肯定的部分：**`MAX_STEPS=8`这个硬上限确实起作用了**——没有出现死循环，8步用完之后老老实实停下、如实报告"未能得出答案"，没有在信息不足的情况下编一个听起来合理但其实是瞎猜的答案。这是这次实验里"安全阀独立于判断准不准"这条设计原则被真实验证有效的一次具体证据，不是纸面上的假设。

## 6. 具体的改进方向（记录下来，不代表现在就要做）

- **最小修复**：把第9题的题目路径改成`"json"`而不是`"flask/json"`，重新跑一次，验证agent能不能答对——这个能验证"agent本身没问题，只是那道题出错了"这个假设。
- **更有价值但成本更高的改进**：给`agent.py`加一层"失败模式检测"——如果连续N次（比如3次）尝试同一个动作都失败，往transcript里加一句明确的提示（比如"你已经连续3次尝试同一个路径都失败了，换一个思路"），而不是指望模型自己从历史记录里悟出来。这其实是给"观察结果"这个信号也做一次类似`diagnose()`的加工，跟`goal_loop.py`给`must_avoid`加固措辞（把"上次具体怎么违反的"讲清楚，而不是让写手自己从违反记录里猜）是同一个思路的复用。

这条改进要不要做、什么时候做，留给下一次决定，这里先如实记录问题本身。

## 7. 修正验证（2026-08-15，当天补验）

把第9题的路径改成正确的`"json"`后单独重新跑了一次，两版都**只用2步**就正确答出（对比之前任何一题至少3步起，这题反而是最快的一次）——证实第4节的诊断是对的：这道题失败纯粹是出题时路径写错，不是agent读代码/判断能力的问题。`eval_set/step3_step1_结果.json`和`step3_step2_结果.json`里第9题的记录已经更新为修正后的结果，原始的"连续8次撞路径失败"记录保留在本文档第2节，不做消音处理。

**但要说清楚，这次修正并没有推翻第4节的核心发现**——修正只证明了"这一道具体的题不是agent的锅"，**没有**证明"agent面对重复失败会主动换策略"这件事本身是成立的。第4节指出的缺陷（失败后只会原地重试、不会主动调整路径）依然是`agent.py`当前设计里一个真实存在、没有被这次修正解决的问题——如果以后遇到一道换了任何路径都会失败的题（比如问一个真的不存在的文件/函数），这个缺陷大概率还会复现。这条改进依然是留待以后决定要不要做的事，不是"已经修好了"。
